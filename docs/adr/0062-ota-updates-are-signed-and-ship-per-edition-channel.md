# OTA updates are signed and ship on the app's one channel

Until 0.9 every change to the app, JavaScript included, reached a reader only through a new native build (ADR 0004). ADR 0007 promised each Edition its own OTA update channel with staged rollout and left the how open. Spec #1293 wires `expo-updates` into the app: the app checks for an update at launch and runs the newest one it accepts. What the app accepts, which build an update may reach, how an update is published and who may publish one are decided here, since an update is code that runs on every reader's phone (security baseline of #1).

**Every update is signed with SLOVO's code-signing key, and the app accepts only an update signed with it.** The public certificate lives in the repository, and the app config names it as the updates' code-signing certificate, so every build embeds it; the private key lives in the EAS environment and never in the repository (it is public, and gitleaks runs in CI). An unsigned update, one signed with another key or one whose signature doesn't check is refused and the app keeps running the code it has. Nobody who cannot sign can push code to readers, whatever they can push to EAS.

**The runtime version is the fingerprint of the native code.** The app config uses the `fingerprint` runtime version policy: the runtime version is computed from the native project (the native modules, the config plugins, the Swift of the widget and the Spotlight module), so two builds share a runtime version exactly when their native code is the same. An update is published for one runtime version and only reaches builds of that version, so an update never runs against native code it was not made for. A native change changes the fingerprint and ships as a new build; readers of the old build go on receiving only updates made for it.

**One channel for the one app.** The Editions live inside one app (ADR 0065), so the app has one Update channel, `updateChannel` in the AppConfig (`app/app.json`), today `uk`. The channel's name comes from the AppConfig and the EAS build profile it names, never from the Core (ADR 0006), and every build of the app is bound to it. About («Про застосунок») shows the app version, the build number and the update id («Версія {version} · збірка {build}», «Оновлення {id}»), so a bug report names the exact code.

**The app checks on launch, with a short timeout, and falls back to what it has.** `expo-updates` checks for an update when the app launches, waits a few seconds at most, and starts the embedded code when the check or the download is slower; an update that arrived runs from the next launch. The app never applies an update in the middle of a session, and a failed check costs the reader nothing but the wait.

**Publishing is a deliberate act, never a side effect of merging.** An update is published by one command run by the owner, or by a `workflow_dispatch` workflow that takes a rollout percentage and publishes to the AppConfig's channel, so no publish names an Edition; a second run widens the rollout, as EAS offers it, so a bad update is caught on a share of readers first. No workflow publishes on push to `main`: `main` is where the code lives, not where readers get it.

**Testing.** The app config is tested in Vitest (ADR 0029 keeps Jest for components and routes): the updates block names the AppConfig's channel, the fingerprint runtime policy and the code-signing certificate, and the config refuses to build a release without them. The About screen's version, build and update id are tested in Jest. Whether an update reaches a phone, whether an unsigned one is refused and whether the rollout widens are the owner's checks on the TestFlight build of 0.9 (ADR 0004).

## Considered Options

- **Unsigned updates, trusting EAS alone**: rejected. Anyone with the EAS account's credentials could push code to every reader; the signing key is one more thing an attacker needs, and it is never in the repository or the CI.
- **A hand-written runtime version (`1.0.0`, `2.0.0`…)**: rejected. The owner would have to notice every native change and bump the version by hand; a forgotten bump ships an update to a build that crashes on it.
- **One channel per Edition**: rejected by ADR 0065. Every Edition ships inside the same app and native project, so one update carries every Edition; the fingerprint still keeps an update off a build whose native code it was not made for.
- **Publish on every merge to `main`**: rejected. `main` takes many small changes a day; readers would receive untested combinations, and nothing could be caught on a share of readers first.
- **Check for updates in the background and apply at once**: rejected. A screen could change under the reader's fingers; the next launch is soon enough for a JavaScript fix.

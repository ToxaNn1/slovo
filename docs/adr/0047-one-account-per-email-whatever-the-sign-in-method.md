# One Account per email, whatever the Sign-in method

Until 0.8.9 the only Sign-in method was a Sign-in code by email (spec #333, ADR 0030): the backend mails a six-digit code, the first right code for an email creates its Account, and better-auth keeps the codes and the Sessions. Spec #603 adds Sign in with Google: the app shows Google's native sheet, gets a Google identity token for the reader and sends it to the backend. The backend must decide what the token proves, which Account it reaches and what refuses it, without trusting the app.

**An email has one Account, and every Sign-in method reaches it.** The Account's identity is its email, as the reader sees it on the SLOVO ID screen. A Google sign-in for an email that a Sign-in code made reaches that Account, and a Sign-in code for an email that Google made reaches that one; the first sign-in of an email creates its Account whichever method it uses. The Account records the methods that signed it in (better-auth's `sign_in_methods`, one row per Google identity, ADR 0030), so an Account names both methods, and deleting the Account deletes them with it. Nothing else changes with the method: the Session the sign-in starts, `me`, sign-out, sign-out everywhere and deletion are the same.

**The backend verifies the token; the app only carries it.** The procedure `account.signInWithGoogle`, `POST /v1/account/google-sessions`, takes the identity token and an Edition id, and the backend checks what Google's documentation asks of a verifier: the signature against Google's published keys, the issuer, the expiry, the audience against SLOVO's client ids and that Google has verified the email. The server Core holds the rule behind a `GoogleVerifier` port, which answers the token's identity (Google's subject, the email and whether it is verified) or why it doesn't check; the backend's adapter verifies with `jose` (`createRemoteJWKSet`, `jwtVerify`): RS256, the issuer, the audience, the expiry and an age of at most an hour, with 30 seconds' tolerance. It keeps Google's keys for the `Cache-Control` max-age of Google's answer and fetches them sooner only for a token signed with an unknown key, at most every 30 seconds; a failure fetching them is an unexpected failure (a 500 and a crash report, ADR 0048), not a bad token. The refusals are the contract's: `INVALID_TOKEN` (401) for a token that is not Google's, doesn't check or has expired, `FOREIGN_AUDIENCE` (401) for a token issued to another app, `EMAIL_NOT_VERIFIED` (403) for an email Google hasn't verified, `NOT_FOUND` for an Edition that doesn't serve Google sign-in, and `TOO_MANY_REQUESTS` with `Retry-After` over the limit of 30 Google sign-ins per IP address in 10 minutes, counted apart from the code checks. A refused token makes no Account.

**The client ids come from the environment, never the repository.** `GOOGLE_CLIENT_IDS` lists SLOVO's OAuth client ids at Google, comma-separated, one per app that signs in with Google; `.env.example` names it with an empty value. With none configured no token can be for SLOVO, so the backend refuses every Google sign-in as `NOT_FOUND`, exactly as when the Edition's `googleSignIn` Feature Switch is off or the owner turned it off remotely (ADR 0040). The switch is per Edition, like `account`, and comes apart from it: an Edition, or the owner in an emergency, can stop Google sign-ins while Sign-in codes keep working.

**The adapter signs in without better-auth's social endpoint.** better-auth's own social sign-in verifies the token itself and answers one error for every reason, so it leaves no way in for the server Core's verifier or its refusals. The Authenticator does what that endpoint would: finds the Account by email or creates it, links the Google identity once, starts a Session through better-auth's internal adapter and hands the token out in the signed form the bearer plugin demands (ADR 0030), the token and its HMAC with `AUTH_SECRET` in base64, as better-auth signs its Session cookie. The tests prove the form by using the token.

**The app's Core shows the sheet through a port and sends the token through another.** The Account module gets a `GoogleSignInSheet` port beside `AccountApi` and `SessionStore`: it answers the identity token of the reader who signed in, that the reader cancelled, or that it found no network or failed otherwise; the shell implements it on Google's SDK (#613), and nothing in the Core knows the SDK. `AccountApi` gets `signInWithGoogle`, which the app's adapter answers from the new procedure. The Google path runs as the one request `signInWithGoogle`, the sheet included, so no other request starts while the sheet is up; it starts only signed out, where its button is. A cancelled sheet leaves the Account as it was, with no problem. The backend's three refusals of a token (`INVALID_TOKEN`, `FOREIGN_AUDIENCE`, `EMAIL_NOT_VERIFIED`) come to the reader as one problem, `refused`, with its own line in the Edition strings: the reader can do nothing different for each, and only try again or sign in with a code. The other problems are the ones every request has (ADR 0037). A Google sign-in lands in the same `signed-in` state as a code, so Sync merges the device's user state into the Account at the first one, as it does for a code (ADR 0041), and sign-out, sign-out everywhere and deletion are the same.

**The app forgets Google's sign-in when its Session ends.** Google's iOS SDK keeps the Google user and its refresh token in the Keychain, so the port has `forget({ revoke })`, which the Account calls whenever the Session ends: sign-out, sign-out everywhere and a Session the server ended with `revoke: false`, deletion with `revoke: true`. The Core doesn't know how the Session started, so it calls it after a Sign-in code too. The shell maps it to the SDK's `signOut()`, after `revokeAccess()` when revoking, and a failure never holds up the sign-out or deletion. The sheet asks for Google's default scopes: the iOS SDK always adds `email` and `profile`, and the privacy policy names what Google hands over.

**The tests** drive Seam 1 with a fake Google (spec #603), and Seam 2 with a fake sheet and a fake Account API in `@slovo/core/testing` that takes the fake sheet's tokens: the fake's sign-in sheet mints tokens and its verifier checks the signature, the expiry against the test's clock and the audience against the backend's client ids, as the real verifier checks Google's. Nothing calls Google in a test, and a token of the real Google is checked once by hand on a real iPhone at the EAS build of 0.9.

## Considered Options

- **The Google subject as the Account's identity**: rejected. The reader sees and types an email; a Sign-in code already keys on it; and a reader whose Google email changes would split into two Accounts, one per method.
- **An Account per Sign-in method**: rejected. The same person would have two SLOVO IDs with two sets of words, and would never know which one a device opened.
- **better-auth's social sign-in endpoint (`signInSocial` with an id token)**: rejected. It verifies the token itself, so the tests can't put a fake Google behind it, and every refusal comes back as one `INVALID_TOKEN`.
- **Verifying the token in the app**: rejected. The backend would then create an Account for any email a client names.
- **better-auth's `verifyGoogleIdToken`**: rejected. It fetched Google's keys on every sign-in and answered `INVALID_TOKEN` when the fetch failed, so a Google outage looked like a bad token.
- **One client id in one variable**: rejected. A Google identity token names the client id of the app that asked for it, and a second Edition's app, or a Web client id beside the iOS one, means a second id; a list costs nothing now and no contract change later.

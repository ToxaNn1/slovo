# Crash reports go to Sentry, with no personal data

Until 0.8.9 a crash on a reader's phone or an unexpected failure of the backend reached nobody: the app had no reporting at all, and the backend only logged the failure on its own host. Before beta testers arrive the owner needs to hear of both. Any report leaves SLOVO for a third-party service, so what crosses the wire must be decided as well as where it goes (spec #603: #606, #607, #650, #661).

**Crash reports go to Sentry, one project for the app and one for the backend, and only with a DSN from the environment.** The backend reads `SENTRY_DSN` and the app reads `EXPO_PUBLIC_SENTRY_DSN`, which the build writes into the bundle. The repository holds no real DSN (it is public, and gitleaks runs in CI); `.env.example` names the backend's with an empty value. Without a DSN nothing reports and neither side loads Sentry's SDK: the backend imports `@sentry/node` only when it has one (`sentry-reporter.ts`), and the app `require`s `@sentry/react-native` only when it has one (`crash-reports.ts`), so a build without a DSN never runs the SDK's module.

**The backend's DSN is https only.** The backend's config refuses a `SENTRY_DSN` that is not an `https://` address and stops at start, naming the variable, as it does for every other wrong setting (#648); an event sent over plain http would cross the network readable. The app's DSN is taken as the build gives it: the app doesn't check its scheme, and Sentry hands out https DSNs.

**The backend reports only an unexpected failure, and only what names it.** A request answered `500` is logged and reported; a refused request (a 4xx) never is. The report (`ErrorReport`, built by `reportOf` in `error-reporter.ts`) is the error's kind, a message with no personal data, the stack's frames (the `at ...` lines, never the message above them) and the request's id as a tag, so the report and the log line find each other. A failed query is named by its SQL, whose values are `$1`, `$2`..., and Postgres's own error by its SQLSTATE and constraint, never its message and detail, which may quote a value; any other error's message is scrubbed. The report carries nothing of the request: no IP address, headers, body or Account. Sentry gets only the report: none of its default integrations runs, it keeps no breadcrumbs, collects no user, cookies, headers, bodies or query parameters, sends no server name, and a `beforeSend` drops any request, user or breadcrumbs an event might still carry.

**The app reports crashes and unhandled errors, and keeps only what finds the bug.** `startCrashReports` runs once, at launch, from the root layout. It sends no default PII, keeps no breadcrumbs, traces nothing (no performance or user-interaction tracing), attaches no screenshot or view hierarchy and records no session replay. Its `beforeSend` drops the event's user, request, breadcrumbs, server name and extra data and the device's name, and scrubs the event's message and each exception's value. The stack's frames, the device's model, the app's release and the environment (`development` or `production`) stay, so the owner can find the bug. A native crash is reported by the SDK's native layer and never passes through `beforeSend`, so the Sentry project itself must store no IP address and scrub emails and long tokens in its messages; the owner sets that up with the DSN at 0.9.

**One scrub takes personal data out of every message.** The scrub replaces every email with `[email]`, every long run of token characters (a Session's token, a Google identity token, an Account's id) with `[token]`, every IPv4 or IPv6 address with `[ip]` and every six-digit number (a Sign-in code) with `[code]`. The backend keeps it in `error-text.ts`, which its reports and its logger share (ADR 0030); the app keeps the same patterns in `personal-data.ts`, which its crash reports and its logger share. The scrub is a safety net under the rules above, not a licence to put personal data in an error: it can't know every shape a value takes.

**The app writes to the device's log only through its one logger.** A release build keeps the device's log where anyone with the unlocked phone and a Mac can read it, so the app logs through `log.ts` (`logError`, `logWarning`), which scrubs the text it is given and the error's message and stack as crash reports are scrubbed (#661). ESLint's `no-console` is an error everywhere in `apps/mobile` but `src/log.ts`, so a new `console` call fails CI instead of leaking.

**The tests** drive both through their seams with fakes: the backend's Seam 1 with a fake reporter that holds the reports a request made, so a test proves a 500 reports and a 4xx doesn't, and what a report holds; the app's with a fake SDK that `startCrashReports` takes, and the logger's through the text it writes. Nothing calls Sentry in a test; a real crash on an iPhone is checked by hand at the EAS build of 0.9, once the DSN is set.

## Considered Options

- **Logs only, no third-party service**: rejected. The backend's log stays on one host nobody watches, and a crash on a reader's phone leaves no log the owner can read.
- **Sentry's default integrations, trimmed in `beforeSend`**: rejected for the backend. They read the request, its headers and the client's IP address on their own; a report built by the backend with nothing else in it can't leak what it never held. The app keeps the SDK's crash handlers, since catching a native crash is the point, and strips the event instead.
- **One scrub module both sides import from `contracts`**: not adopted. `contracts` holds what the app and the backend exchange, not code either runs on its own data, and the patterns are a few lines that change together, by review.
- **A DSN in the repository, as Sentry's guides show**: rejected. The repository is public; anyone could send events to the owner's projects.

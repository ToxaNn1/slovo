# The widget reads a Widget Snapshot the Core builds

The master spec put the local database in the App Group's shared container, so the SwiftUI widget (ADR 0001) could read the user state and the Language Pack itself. 0.6 does not. The Core builds a Widget Snapshot: everything each Widget Mode may show, already decided and ready to draw. The app writes it as one JSON file into the App Group's container, and the widget only reads that file, picks an Entry and draws it. This supersedes the master spec's line "local database location: the App Group shared container". ADR 0001's "the widget reads data the app shares through an App Group" still holds.

The composition's `widget.snapshot()` builds it from the Entries module (ADR 0015), Favorites, Collections and the onboarding state, as pure data. It holds a format version, the Edition id, the instant it was written (from the injected clock), whether the onboarding is finished, and each Entry any mode may show, once: its id, kind, headline, second line and VoiceOver text. Then the modes, as Entry ids: Усі слова is every Eligible Entry; Улюблене is the Favorites that are Eligible Entries, newest first; each Collection, newest first and empty ones too, carries its id, its name and its Eligible Entries, newest first. So a Hidden Entry, a Hidden Category, a Retired Word, Correction or Idiom and a kind the Edition turns off never reach the home screen, and Swift holds no rule about them.

The Core and the Edition decide the text, not Swift. A Word's headline is its Lemma with each valid Stress as the combining acute mark, as on the Entry card, and its second line is the primary Definition. A Correction's headline is its main standard equivalent, and its second line is the non-standard form it replaces. An Idiom's headline is its expression, and its second line is its primary Definition; a place name shows the same. The VoiceOver text is the headline and the second line in whole words, with no Stress mark, since the voices break a word at the mark. The widget only truncates with SwiftUI's line limits and scale factor, and adds the Widget Mode's name and its other labels from the Edition's strings.

The contracts package holds the schema, `WidgetSnapshotSchema`, and `serializeWidgetSnapshot`, which checks a snapshot against the schema before it turns it into the file's text, so the app never writes a file the widget can't decode. The schema also requires each Entry once and every id of every mode to be one of its Entries. Each Edition keeps an example built from its own Language Pack, `editions/<id>/widget-snapshot.example.json`, which the widget's gallery preview shows; a contract test parses it, so a schema change that forgets the Swift side fails in CI. A change the widget can't read takes the next format version.

The app writes the snapshot when the composition opens and every time the app goes to the background: every change a reader can make (Favorites, Collections, a hide, the Mix) happens in the app, so leaving it is when the home screen needs the new state. The write is whole-file and atomic (a temporary file in the same container, then a rename), so the widget never reads half a file. After each write the app asks WidgetKit to reload the SLOVO widget's timelines. A failed write is ignored: the widget keeps the last good file, and the next move to the background tries again. About 550 Entries with short text stay well under 1 MB, so there is no paging.

The widget never writes. An Entry opened from the widget is Seen by the same one-write rule as one opened from a notification (ADR 0013's 0.4 amendment), through the composition.

## Considered Options

- **The widget reads the user state and the Language Pack in the App Group**, as the master spec said: rejected. Swift would copy the Core's rules for Eligible Entries (ADR 0015), the Mix, Hidden Entries and Categories, Retired Words and Corrections and the kind switches, and the JSON encoding of every record (ADR 0013), so the Core would no longer be the one place those rules live. iOS also ends an app that holds a SQLite lock on a file in a shared container when it is suspended (the `0xdead10cc` termination), and the user state is written often (Seen marks, History). Keeping both where they are also spares 0.6 a file move and a migration.
- **The snapshot holds the ids only, and the widget reads the Language Pack for the text**: rejected. The Language Pack would still move into the App Group, and Swift would apply the Stress marks and pick the second line itself.
- **One file per Widget Mode**: rejected. The modes share most Entries, a reader's change touches several modes at once, and one atomic file can never mix an old mode with a new one.

## Amendment: how the widget extension is built and the snapshot reaches it (0.6)

The widget's Swift code lives in `apps/widget`. At prebuild `@bacons/apple-targets` links that folder into the Xcode project as a widget extension, a synchronized folder, so Xcode takes every file in it and nothing in `ios/` is kept in git. The extension's bundle id is the Edition's plus `.widget`, and it gets the app's App Group, `group.` plus the Edition's bundle id. Swift holds no Edition data: before the target is linked, the app config writes the Edition's part into `apps/widget` (`apps/mobile/widget-extension.ts`), none of it kept in git. That is the colour tokens the widget draws with as colour sets and the divider band (Decor slot 2) as a vector image, both light and dark; the Edition's fonts; the `widget` strings in the Edition's language; the example Widget Snapshot for the gallery; and an `Info.plist` naming the fonts, the App Group, the URL scheme and the font families.

The app writes the snapshot as `widget-snapshot.json` in the App Group's container through `expo-file-system`, staged first as `widget-snapshot.staged.json`. That module's rename over an existing file removes the old file before it moves the new one in, so the rename is two steps, not one. For the moment between them the whole new snapshot is still the staged file, so the widget reads the staged file whenever `widget-snapshot.json` is missing, then `widget-snapshot.json` once more in case the rename finished in between, and always finds a whole snapshot. After the rename the app asks WidgetKit to reload every timeline of the app, which is the SLOVO widget's. Writes run one after the other, so an older snapshot never lands last. A dev client built before 0.6 lacks the two native modules (`expo-file-system` and the Apple targets' storage module), so the shell asks `nativeModules` and writes nothing there.

### Considered Options

- **A native module of SLOVO's own that renames with one `rename(2)`**: rejected. It is more native code for every Edition to build, for a moment that the staged file already covers.
- **The snapshot in the App Group's `UserDefaults`, through the Apple targets' storage module**: rejected. The snapshot is one file the contract test checks byte for byte against its schema, and `UserDefaults` is meant for small values, not a document of hundreds of Entries.

## Amendment: each widget chooses its Widget Mode (0.6)

The Widget Mode lives in iOS's widget configuration (the iOS 17 App Intents configuration), not in the user state, so each widget on the home screen keeps its own and the app stores nothing. The mode parameter offers Улюблене, Колекція and Усі слова, Усі слова by default. The Collection parameter lists the snapshot's Collections and is keyed by Collection id. The widget never trusts a name it stored: each timeline looks the id up in the latest snapshot, so a renamed Collection shows its new name, and an id the snapshot no longer holds stays chosen, so the widget can say its Collection was deleted instead of quietly falling back to another mode.

The widget picks the mode's ids and the empty or broken state from the snapshot; which Entries a mode may show is still the Core's. No snapshot yet, the onboarding unfinished, or Усі слова with no Entry (every one hidden or out of the Mix) shows «Відкрийте SLOVO»; Улюблене with no Entry, an empty Collection, a deleted Collection and Колекція with no Collection chosen each say so. These states wait for the app's next reload rather than asking WidgetKit for another timeline. A tap on a state opens the app's root link, which is the Feed.

All the text is the Edition's `widget` strings, written into the extension's string table: the mode names and both parameters' titles, the overline of each mode («КОЛЕКЦІЯ · {name}» takes the Collection's name, which the widget fills in) and the states. The overline is drawn in capitals, so a Collection's name follows the design.

## Amendment: a switched-off widget stops updating (0.8.5)

With the `widget` Feature Switch off (ADR 0040), by its effective value at the time of the call, `widget.snapshot()` builds nothing, so the app writes no new Widget Snapshot and asks WidgetKit for no reload. The widget keeps the last file and just stops updating; there is no placeholder, and no native change, since the extension already shows what it last read. With the switch on again the next write is as before.

## Amendment: only the widget's links open as the widget's (0.8.9)

The app's scheme can't tell who opened a link, so the security review (#617, F5) found that any app or web page could open `entry/<id>?from=widget` and make the reader's History list Entries they never read, or name the label of «Назад». Expo Router hands every link from outside the app to `app/+native-intent.tsx` and none from inside it. There a link keeps its path and drops every search param, so «Назад» shows the app's own label and the Entry opens as a plain link: not Seen, in no History. A notification never comes from outside: the app opens a tapped one's Word inside it, so `from=notification` from outside is dropped too.

Only the widget's link to an Entry keeps `from=widget`, and only with the key of the Widget Snapshot the widget reads now. The snapshot carries that key as `linkKey`, which the app adds to the Core's snapshot (the contracts allow it, the Edition's example has none), and the widget appends it to its links as `key=`. The app keeps one key for the app run: the one of the snapshot in the App Group, which the links on the home screen carry already, or, with none there, a new one from the random source, which the next snapshot takes there. No other app or web page can read the App Group, so none can make a link that passes for the widget's. A widget built before 0.8.9 sends no key, so its links open as plain links until the next build.

### Considered Options

- **Every link from outside the app opens as a plain link**, the widget's too: rejected. An Entry opened from the widget would no longer be Seen, against this ADR.
- **The key in a file or a store of its own**: rejected. The snapshot is already the one file the app writes and the widget reads, and its schema is checked on both sides.
- **The Maestro flows open the widget's and a notification's links**: no longer possible, as Maestro can neither read the key nor tap a notification; the smoke opens forged links and checks that History stays empty, and the Jest tests of the outside links cover the real ones.

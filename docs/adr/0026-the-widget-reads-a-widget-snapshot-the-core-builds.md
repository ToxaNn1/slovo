# The widget reads a Widget Snapshot the Core builds

The master spec put the local database in the App Group's shared container, so the SwiftUI widget (ADR 0001) could read the user state and the Language Pack itself. Instead, the Core builds a Widget Snapshot: everything each Widget Mode may show, already decided and ready to draw. The app writes it as one JSON file into the App Group's container, and the widget only reads that file, picks an Entry and draws it. The widget never writes.

**What it holds.** The composition's `widget.snapshot()` builds it as pure data from the Entries module (ADR 0015), Favorites, Collections and the onboarding state: a format version, the Edition id, the instant it was written (from the injected clock), whether the onboarding is finished, and each Entry any mode may show, once, with its id, kind, headline, second line and VoiceOver text, all from the Entry row (ADR 0017). Then the modes, as Entry ids: Усі слова is every Eligible Entry; Улюблене is the eligible Favorites, newest first; each Collection, newest first and empty ones too, carries its id, its name and its Eligible Entries, newest first. So nothing ineligible ever reaches the home screen, and Swift holds no rule about it. The widget only truncates with SwiftUI's line limits and adds the Widget Mode's name and labels from the Edition's strings. With the `widget` Feature Switch off (ADR 0040) `widget.snapshot()` builds nothing, so no new file is written and the widget keeps showing the last one.

**The contract.** The contracts package holds `WidgetSnapshotSchema` and `serializeWidgetSnapshot`, which checks a snapshot against the schema before writing, so the app never writes a file the widget can't decode. The schema requires each Entry once and every id of every mode to be one of its Entries. Each Edition keeps an example built from its own Language Pack, `editions/<id>/widget-snapshot.example.json`, which the widget's gallery preview shows and a contract test parses, so a schema change that forgets the Swift side fails in CI. A change the widget can't read takes the next format version.

**Writing.** The app writes the snapshot when the composition opens and every time the app goes to the background, since every change a reader can make happens in the app. It writes `widget-snapshot.json` through `expo-file-system`, staged first as `widget-snapshot.staged.json` and then renamed. That rename removes the old file before moving the new one in, so the widget reads the staged file whenever `widget-snapshot.json` is missing, then `widget-snapshot.json` once more in case the rename finished in between, and always finds a whole snapshot. Writes run one after the other, so an older snapshot never lands last. After each write the app asks WidgetKit to reload the app's timelines. A failed write is ignored: the widget keeps the last good file. About 550 Entries stay well under 1 MB, so there is no paging. A dev client without `expo-file-system` and the Apple targets' storage module writes nothing.

**The extension.** The widget's Swift code lives in `apps/widget`. At prebuild `@bacons/apple-targets` links that folder into the Xcode project as a synchronized folder, so nothing in `ios/` is kept in git. Its bundle id is the Edition's plus `.widget`, with the app's App Group, `group.` plus the Edition's bundle id. Swift holds no Edition data: the app config (`apps/mobile/widget-extension.ts`) writes the Edition's part into `apps/widget` before linking, none of it kept in git: the colour tokens as colour sets and the divider band (Decor slot 2) as a vector image, light and dark; the fonts; the `widget` strings; the example snapshot; and an `Info.plist` naming the fonts, the App Group and the URL scheme.

**Each widget chooses its Widget Mode** in iOS's App Intents configuration, so each widget keeps its own and the app stores nothing. The mode parameter offers Улюблене, Колекція and Усі слова (the default); the Collection parameter lists the snapshot's Collections, keyed by id. Each timeline looks the id up in the latest snapshot, so a renamed Collection shows its new name and a deleted one says so instead of falling back to another mode. No snapshot yet, the onboarding unfinished, or Усі слова with no Entry shows «Відкрийте SLOVO»; Улюблене with no Entry, an empty or deleted Collection and Колекція with none chosen each say so. These states wait for the app's next reload. A tap on a state opens the Feed. All text is the Edition's `widget` strings; the overline («КОЛЕКЦІЯ · {name}») is drawn in capitals.

**Opening an Entry.** An Entry opened from the widget is Seen by the same one-write rule as one opened from a notification (ADR 0013), through the composition. Since the app's scheme can't tell who opened a link, only the widget's link, `entry/<id>?from=widget`, opens as the widget's, and only with the key of the current Widget Snapshot. The app adds that key to the snapshot as `linkKey` (the contracts allow it; the Edition's example has none), and the widget appends it to its links as `key=`. The app keeps one key per app run: the one already in the App Group, or a new one from the random source. No other app can read the App Group, so none can forge the widget's link. Expo Router hands every link from outside the app to `app/+native-intent.tsx`: there a link to an Entry on any of its routes (`entry`, the Game, Favorites, History, Learning, a Collection), whatever its slashes (each run of `/` counts as one, a trailing `/` as none) and also inside the dev client's link (`<scheme>://expo-development-client/?url=<link>`), keeps its path and drops every search param, so it opens as a plain link: not Seen, in no History, with the app's own «Назад» label. The one exception is the widget's `entry/<id>` carrying the current key, which keeps `from=widget`. A notification never comes from outside, so `from=notification` from outside is dropped too. Every other link goes on to Expo Router as it came.

## Considered Options

- **The widget reads the user state and the Language Pack in the App Group**, as the master spec said: rejected. Swift would copy the Core's rules for eligibility and the encoding of every record (ADR 0013), and iOS ends a suspended app that holds a SQLite lock on a file in a shared container (`0xdead10cc`), while the user state is written often.
- **The snapshot holds ids only, and the widget reads the Language Pack for the text**: rejected. The Language Pack would still move into the App Group, and Swift would apply the Stress marks itself.
- **One file per Widget Mode**: rejected. The modes share most Entries, and one atomic file never mixes an old mode with a new one.
- **A native module of SLOVO's own that renames with one `rename(2)`**: rejected. More native code for every Edition, for a moment the staged file already covers.
- **The snapshot in the App Group's `UserDefaults`**: rejected. The snapshot is one document the contract test checks against its schema, and `UserDefaults` is meant for small values.
- **Every link from outside the app opens as a plain link**, the widget's too: rejected. An Entry opened from the widget would no longer be Seen.
- **The key in a file or store of its own**: rejected. The snapshot is already the one file the app writes and the widget reads.

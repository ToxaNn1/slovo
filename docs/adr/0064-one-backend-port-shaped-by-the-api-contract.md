# One Backend port shaped by the API contract

Until now the Core reached the backend through eight ports (`AccountApi`, `SyncApi`, `ReportsApi`, `CollectionLinksApi`, `ContentApi`, `CommunityWordApi`, `SwitchesApi`, `CountersApi`), each with its own failure union. Every port had one production adapter in the app, a pass-through over `answerOf` in `apps/mobile/src/api.ts`, and one hand-written fake in the Core. The mapping of no answer, a 429 and a 5xx to `RequestFailure` (ADR 0037) lived in the app, so the Core could not test how a feature behaves on each failure, and every fake re-encoded it. One new endpoint cost a port, a failure union, a fake, a `testing.ts` export, a barrel export, an app adapter, an adapter test and a key on `openComposition`. The architecture review of 30.10 rated this the strongest deepening.

The Core has one Backend port, `Backend` in `packages/core/src/ports.ts`: the API contract's client, `ApiClient` of `@slovo/contracts/api`, one function per procedure. The interface is the contract itself (ADR 0031), so a new procedure adds nothing to the port, the fake or the shell.

- **The shell supplies only the client.** `apps/mobile/src/api.ts` builds it once with `createApiClient` and the backend's address; the app has no API adapters. The client sends a call's Session, named as `context.token`, as `Authorization: Bearer`, and a 429 throws `TooManyRequestsError`, which carries the seconds of the answer's `Retry-After`.
- **The Core answers, retries and maps.** `answerOf` in `packages/core/src/backend.ts` turns every answer of a call into a value, and `withRetries` in `packages/core/src/retry.ts` is the one retry rule (below). `RequestFailure` carries `retryAfter` on `too-many-requests`, so no module reads a header.
- **Each module keeps its own `Pick` of the port** (`Pick<Backend, 'sync'>`, `Pick<Backend, 'collectionLinks' | 'counters'>` for the composition) and calls the backend directly, through `answerOf` with the failure mapping of its procedures. The per-feature failure unions callers still read (`AccountApiFailure`, `SyncApiFailure`, `ReportsApiFailure`, `CollectionLinksApiFailure`) are types derived inside the Core, next to their modules. `openComposition` takes one `backend`, for the Community Word and the Collection Links; the Account, Sync, Mistake Reports, the content update, the remote switches and the Community Counters, which open apart (ADR 0037), take it too.
- **One fake backend.** `@slovo/core/testing` exports `createFakeBackend`: the contract served in process by `serveApi` (below), its procedures answering like the backend's over state held in memory, and `backend`, the port over it. A test reads and sets the state by domain and makes requests fail by reason, whatever the procedure or naming one; a request the fake fails as unanswered loses its answer on the way back, so `offline` is a real no answer. The Core's tests cover how each feature behaves on no answer, a 429 and a 5xx, with the contract served in process, where the app's adapter tests did.

## Answers and the retry rule

- **Every answer is a value.** `answerOf` turns every answer of a call into a value: a Core module's request never rejects. An error the contract defines for the procedure becomes the module's failure, typed by the contract; otherwise no answer is `offline`, a 429 `too-many-requests`, with the seconds of the answer's `Retry-After`, a 5xx `server-error`, and anything else `unexpected`.
- **One retry rule.** Every Core request to the backend tries again through `withRetries`: only no answer or a 5xx is tried again, at most 3 times; before the nth try it waits between half and all of 1 s × 2ⁿ⁻¹, drawn from the injected `Random`, through the injected `Schedule`. A 429, an `unexpected` answer or a code the contract defines is never tried again.
- **A 429.** The Account shows `too-many-requests` at once (ADR 0037). Sync, which runs in the background, waits for the answer's `Retry-After` instead (ADR 0041), as Mistake Reports and the Community Counters do; the Content update module waits for its next due check.
- **Values come from the contracts.** `@slovo/contracts` holds `SIGN_IN_CODE_DIGITS`, `SignInCodeSchema`, `AccountEmailSchema` and `PublishedPack` once; the Core, the server Core and the code field derive from them. The `/v1` API still takes the email as typed.
- **The Game's retry of its planning** (ADR 0024) stays apart: it reads the Language Pack on the device, with no server to spare.

## Tested against the contract served in process

`@slovo/contracts/api/test-support` exports `serveApi(procedures)`. It implements `apiContract` with oRPC's `implement`, serves it through oRPC's OpenAPI handler in process, as the backend serves it, and returns the `fetch` a test gives `createApiClient`. A test writes only the procedures it needs, each a handler typed by the contract: it gets the procedure's `input`, the request's `context.headers`, where a Session travels, `context.resHeaders`, the headers the answer gets (as on the backend, such as a 429's `Retry-After`), and the procedure's `errors`, and returns the output or throws. Any failure but a refusal (4xx), such as a procedure the test leaves out, answers the backend's bare `500 { code: "INTERNAL" }` (ADR 0031). `refusal(code, context, { retryAfter })` is the error a procedure throws to refuse with one error code of the contract, with the status the code has, typed by the contract, so renaming a code fails typecheck; `failingWith(code)` makes every procedure refuse with it. `answeringWith(status, body)` is a proxy's answer, which is no answer of the contract, and `fileOf` a file a procedure answers.

- **The Core's tests cross the contract.** `packages/core/src/backend.test.ts` asserts what a procedure got, its input and the Session it carried, and what `answerOf` makes of the contract's outputs and error codes, of no answer, of a 429 with its `Retry-After` and of a 5xx; the tests of each feature run it through the composition over the fake backend, so a module's behaviour on each failure is tested in the Core. Addresses and encoding come from the contract on both sides, so a test fails on a mismatch with the contract, not on a renamed path. Only what never reaches the backend is still a `fetch` of the test's own: a proxy's 502 page, or a request that gets no answer.
- **A test-only entry point.** The helper has its own entry point beside `@slovo/contracts/api`, so the package's main entry and the API client load no oRPC server code (ADR 0031). `@orpc/server` is a dev dependency of `contracts`, and only a test, a test-support module or the Core's fakes may import the helper (dependency-cruiser's `only-tests-serve-the-api-in-process`). Unlike a package's own `test-support.ts` (ADR 0027), it is shared, since it belongs to the contract, which both sides import.
- **The backend's tests stay.** They go on serving the real composition root over Postgres. The helper is for a test that needs a backend of its own, such as the Core's.

## Considered Options

The interface was designed twice:

- **A hand-written `Backend` with the per-feature methods and failure unions kept**, the eight ports as one: rejected. It is as wide as its implementation: every endpoint still adds a method, a failure union, a fake method and an adapter method, and the failure mapping stays in the shell and in each fake. The interface of a port is what the shell must implement; the shallower it is, the more it costs to extend.
- **The client type of the contract** (chosen): the contract is already the one description of the API (ADR 0031), and oRPC derives the client from it, so the port has no text of its own to keep in step. The depth is in `answerOf` and `withRetries`, which every feature shares, and in `serveApi`, which every test shares. ADR 0031, the contract, and `serveApi`, the contract served in process, are what make it possible.
- **A fake `fetch` with hand-written answers** in the Core's tests: rejected. It is the second description of the API that ADR 0031 rejects for the app's code.
- **The Core's tests against the real backend**: rejected. The app imports neither the backend nor the server Core (ADR 0030), and its tests would need Postgres.
- **oRPC's in-memory router client**, which calls the procedures without HTTP: rejected. It skips the OpenAPI encoding of input, output and errors, which is what the client crosses.
- **The helper in a package's own `test-support.ts`**: rejected. It describes the contract, not the app, and a test of the backend could not use it.
- **Fixed delays (1, 2, 4 s) for backend requests**: rejected. Without jitter every device that failed at once tries again together.
- **Try again on every failure, or on a 429 with `Retry-After`**: rejected. A wrong code or an ended Session doesn't pass by itself, and a limit's window outlasts the tries; each try counts against the per-IP limits.
- **The Core reads `Retry-After` through a `fetch` it wraps**, as the app's adapters did: rejected. HTTP stays in the contract's client; the Core sees a value on the error.
- **The Core avoids loading oRPC** by mapping the client's errors by shape: rejected. `safe` and `ORPCError` are the contract's own vocabulary, typed by the contract, and the app loads them anyway; the Core loads no HTTP server code and no React.

# Remote Feature Switches only turn features off

Until 0.8 a Feature Switch lived only in an Edition's `edition.json`, read by the app and the backend alike (ADR 0008, 0030). Turning a broken feature off in one Edition took a new build and an App Store review. Spec #378 adds remote switches on the backend for that emergency: the owner turns a feature off in one Edition with one local command, and the apps and the backend stop offering it, without a build. ADR 0008 kept switches "in the database"; ADR 0030 moved them into the Edition config until this arrived.

**A remote switch only turns a feature off.** It can't turn on a feature the Edition turns off, so the backend can never switch on what an Edition hasn't shipped. The effective value of a Feature Switch is the Edition's value and not off remotely, and every reader of a Feature Switch, in the app and on the backend, reads the effective value.

- **Storage.** The `remote_switches` table holds one row per Edition and feature: the `edition_id`, the feature by its Feature Switch's name, whether it is `off`, and `set_at`, when it was last set. Clearing a switch keeps its row with `off` false, so the row tells when its switch last changed. The server Core's `edition` domain reaches the table through a `RemoteSwitchStore` port, which keeps names and never reads them.
- **Setting them.** Two local commands of the backend, in the style of `pnpm publish:pack`: `pnpm switch:off <edition-id> <feature>` turns a feature off, `pnpm switch:clear <edition-id> <feature>` clears its switch, on the database `DATABASE_URL` names. Both go through the Edition registry (`switchOff`, `clearSwitch`), which refuses an Edition the backend doesn't find in `EDITIONS_DIR` and a feature the Feature Switches schema of the contracts doesn't know, so a typo can't make a switch nobody reads. Turning off a feature already off, or clearing one that is on, changes nothing. An admin panel waits for 2.x.
- **Serving them.** The contract's `edition.switches`, `GET /v1/editions/{editionId}/switches`, needs no Session and answers `{ off: [...] }`, the features turned off remotely, in name order. Its ETag is the SHA-256 of that answer, so the same switches always get the same ETag, and an `If-None-Match` that names it gets 304 without a body. An Edition the backend didn't find is `NOT_FOUND`. A feature is named by a plain string, not an enum of the schema's names: an output enum may only narrow within `/v1` (ADR 0031), so an enum would break the API with every new Feature Switch. An app skips a name it doesn't know. A row of a name the schema no longer knows is served as nothing.
- **The backend obeys them too.** `EditionRegistry.serving(editionId, feature)` reads the remote switches after the Edition's own, so a feature off remotely answers `{ ok: false, reason: 'switched-off' }` and its procedures `NOT_FOUND`, like a feature the Edition turns off. An old app can't keep using it. `serving` is now asynchronous. It reads the Edition's rows at every request of a feature the Edition turns on, one query on the table's primary key, so a switch set by the command, in another process, holds from the next request, with no restart.
- **The app** asks for the switches at launch and on each return to the foreground, keeps the answer as a `device-only` record and reads it at launch before the composition opens; offline it uses the cached answer, and without one the Edition's values. Its modules read the effective value each time they act. The amendment below has the details.
- **The `sync` Feature Switch** comes apart from `account`, so sync can be turned off remotely while signing in, signing out and deleting the Account keep working. The commands accept every name the schema knows, `sync` too once it is there.

This amends ADR 0008 and ADR 0030: Feature Switches come from the Edition config, and the backend's remote switches can only turn them off.

## Considered Options

- **Switches in the Edition config only**, as in 0.7: rejected. Turning a broken feature off would still take a build and a review.
- **Remote switches that turn features on too**: rejected. The backend could switch on a feature an Edition hasn't shipped or its build can't run, and a mistake in the table would reach every reader.
- **`edition.switches` answering every effective value**: rejected. The app knows its Edition's own values, and an answer keyed by every switch name would change its shape with every new Feature Switch.
- **The backend keeping the switches in memory**: rejected. The commands run in another process, so a running server would need a restart or a notification to obey a switch, which is the emergency this is for. One lookup per request is cheap at this scale.
- **Deleting the row on clear**: rejected. The row with `off` false tells when the switch was last cleared, at no cost.

## Amendment: the app side (0.8, #389)

The Core's `openRemoteSwitches` (`packages/core/src/edition/remote-switches.ts`) owns every rule of the app side, behind a `SwitchesApi` port that the shell implements on the contract's client (`apps/mobile/src/edition/switches-api.ts`, tested against `serveApi`, ADR 0039).

- **It opens first.** The shell opens it once per app run over the user state, before the Language Pack and the composition. It reads the last answer the device kept, the `device-only` record `edition.switches`, holding the names turned off and their ETag. Without the record, or when it can't be read, no feature is off remotely and the Edition's values hold, offline too.
- **One Edition in effect.** It gives the Edition as the app runs it: the Edition's own object with `isFeatureEnabled` at the effective value, the Edition's value and not off in the last answer. Everything that read the Edition's switches reads this one instead: the composition, the Language Pack's content updates at launch, the tabs, the Mix and Hidden screens, the Settings row of SLOVO ID and its screen, and the lifecycle before a content update check or an Account refresh. No Core module changes for it. Its `isFeatureEnabled` reads the last answer each time it is called, so a module that keeps the Edition, such as the Sync module, acts on the effective value each time. A name the app doesn't know is skipped.
- **When it asks.** The lifecycle asks at launch and on each return to the foreground, naming the kept ETag, so an unchanged answer is a 304 without a body. A request tries again by ADR 0037's one rule; a failure keeps the answer the app has. A new answer is kept for the next launch.
- **A changed answer reopens.** When an effective value changes, the ask resolves `true`, the module makes a new Edition object and tells its subscribers. The lifecycle then reopens the composition (ADR 0036 amendment), which reads the new values where it read them at open, such as the Game's switch and the onboarding's SLOVO ID step, and makes the notification plan as it opens; the lifecycle writes the Widget Snapshot again, as a launch does. Screens bound to the Edition in effect draw again, so the Game tab goes and comes back while the app runs, and a reader on the Game screen when it goes is taken Home. An answer that changes no effective value, such as one that turns off a feature the Edition turns off already, reopens nothing. The settings are not reopened: they read no Feature Switch.
- **With `account` off** the SLOVO ID row, its screen and the onboarding's step are absent, the Session stays in the Keychain and the Account is not refreshed; it comes back as it was once the switch is cleared. **With `contentUpdates` off** no update is checked for, and from the next launch the app opens the bundled pack; the Content update module opens at launch only, so once the switch is cleared checks come back at the next launch.

### Considered Options

- **Ask only at launch**: rejected. An emergency would reach a reader only after they quit the app, which iOS may keep running for days.
- **Reopen at every answer**: rejected. Every return to the foreground would rebuild the composition for nothing; the ETag and the comparison of effective values keep the reopen for a real change.
- **An immutable Edition per answer, read once by each module**: rejected. The Account and the Sync module open apart from the composition and are not reopened, so they would act on the values of the launch until the next one.
- **Make the shell's `edition` itself follow the switches**: rejected. It is read at module load, before the user state that keeps the answer opens, and a hidden mutable value would make every reader of it order-dependent.

## Amendment: one module answers what the reader is shown (architecture review 3)

The screens and the shell's helpers each read the Edition in effect for themselves, and three thin helpers (`tabsOf`, `entryButtonsOf`, `progressShownOf`) passed `isFeatureEnabled` through, so a rule that combined a switch with a setting, such as Self-check, sat inline and untested. Now the shell's `shownOf` (`apps/mobile/src/shown.ts`) answers, from the Edition in effect, the reader's settings and their Mix, what the reader is shown: the tabs, the Game Review, the switchable buttons of an Entry card, Self-check and its setting, «Вчу», the statistics with their Streak and knowledge rows, and the Sync status line. Screens read it through `useShown`, which draws again when a switch in effect, a setting or the Mix changes; the settings are still not reopened on a switch change. UI components get the shape they draw, not a switch: the Game Review is drawn while `GameResult` has `onOpenEntry`, the «Вчу» card and the Self-check row are left out by their screen, and the stats sheet takes which knowledge rows it draws. Modules that act rather than draw, such as the Mix and Hidden screen models, the content updates and the Account, keep reading the Edition in effect.

With Corrections off, or the reader's Mix without Corrections, the statistics' row of the Known Entries shows the Known Words alone, «Знаю 12 слів», without the Known Corrections (owner decision 19.10, #478).

## Amendment: the Rarity Floor's switch is `rarityFloor` (whole-project review fix, B8)

The Feature Switch of the Mix's Rarity Floor was named `rarityFilter`, a word the glossary lists under the Mix's _Avoid_. It is renamed `rarityFloor` in the contracts, every `edition.json`, and every reader in the Core, the app and the backend (owner decision 21.10). No API shape changes: `edition.switches` names features by plain strings. A `remote_switches` row still named `rarityFilter` is a name the schema no longer knows, so it is served as nothing and the commands refuse it, and the feature's own value holds. An owner who turned the Rarity Floor off remotely under the old name sets it again with `pnpm switch:off <edition-id> rarityFloor`.

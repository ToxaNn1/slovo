# Remote Feature Switches only turn features off

Until 0.8 a Feature Switch lived only in an Edition's `edition.json`, read by the app and the backend alike (ADR 0008, 0030). Turning a broken feature off in one Edition took a new build and an App Store review. Spec #378 adds remote switches on the backend for that emergency: the owner turns a feature off in one Edition with one local command, and the apps and the backend stop offering it, without a build. ADR 0008 kept switches "in the database"; ADR 0030 moved them into the Edition config until this arrived.

**A remote switch only turns a feature off.** It can't turn on a feature the Edition turns off, so the backend can never switch on what an Edition hasn't shipped. The effective value of a Feature Switch is the Edition's value and not off remotely, and every reader of a Feature Switch, in the app and on the backend, reads the effective value.

- **Storage.** The `remote_switches` table holds one row per Edition and feature: the `edition_id`, the feature by its Feature Switch's name, whether it is `off`, and `set_at`, when it was last set. Clearing a switch keeps its row with `off` false, so the row tells when its switch last changed. The server Core's `edition` domain reaches the table through a `RemoteSwitchStore` port, which keeps names and never reads them.
- **Setting them.** Two local commands of the backend, in the style of `pnpm publish:pack`: `pnpm switch:off <edition-id> <feature>` turns a feature off, `pnpm switch:clear <edition-id> <feature>` clears its switch, on the database `DATABASE_URL` names. Both go through the Edition registry (`switchOff`, `clearSwitch`), which refuses an Edition the backend doesn't find in `EDITIONS_DIR` and a feature the Feature Switches schema of the contracts doesn't know, so a typo can't make a switch nobody reads. Turning off a feature already off, or clearing one that is on, changes nothing. An admin panel waits for 2.x.
- **Serving them.** The contract's `edition.switches`, `GET /v1/editions/{editionId}/switches`, needs no Session and answers `{ off: [...] }`, the features turned off remotely, in name order. Its ETag is the SHA-256 of that answer, so the same switches always get the same ETag, and an `If-None-Match` that names it gets 304 without a body. An Edition the backend didn't find is `NOT_FOUND`. A feature is named by a plain string, not an enum of the schema's names: an output enum may only narrow within `/v1` (ADR 0031), so an enum would break the API with every new Feature Switch. An app skips a name it doesn't know. A row of a name the schema no longer knows is served as nothing.
- **The backend obeys them too.** `EditionRegistry.serving(editionId, feature)` reads the remote switches after the Edition's own, so a feature off remotely answers `{ ok: false, reason: 'switched-off' }` and its procedures `NOT_FOUND`, like a feature the Edition turns off. An old app can't keep using it. `serving` is now asynchronous. It reads the table at every request of a feature the Edition turns on, one lookup by primary key, so a switch set by the command, in another process, holds from the next request, with no restart.
- **The app** (its own ticket of spec #378) asks for the switches at launch and on each return to the foreground, keeps the answer as a `device-only` record and reads it at launch before the composition opens; offline it uses the cached answer, and without one the Edition's values. Its modules read the effective value each time they act.
- **The `sync` Feature Switch** comes apart from `account`, so sync can be turned off remotely while signing in, signing out and deleting the Account keep working. The commands accept every name the schema knows, `sync` too once it is there.

This amends ADR 0008 and ADR 0030: Feature Switches come from the Edition config, and the backend's remote switches can only turn them off.

## Considered Options

- **Switches in the Edition config only**, as in 0.7: rejected. Turning a broken feature off would still take a build and a review.
- **Remote switches that turn features on too**: rejected. The backend could switch on a feature an Edition hasn't shipped or its build can't run, and a mistake in the table would reach every reader.
- **`edition.switches` answering every effective value**: rejected. The app knows its Edition's own values, and an answer keyed by every switch name would change its shape with every new Feature Switch.
- **The backend keeping the switches in memory**: rejected. The commands run in another process, so a running server would need a restart or a notification to obey a switch, which is the emergency this is for. One lookup per request is cheap at this scale.
- **Deleting the row on clear**: rejected. The row with `off` false tells when the switch was last cleared, at no cost.

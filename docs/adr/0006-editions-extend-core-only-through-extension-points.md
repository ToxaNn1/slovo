# Editions extend the Core only through switches, extension points and decor

An Edition can change what it gets from the Core in three ways only:

- turn Core features on or off with Feature Switches;
- plug its own behaviour or UI into Extension Points the Core defines (Game modes, Word card sections, language services);
- supply Decor, design tokens and the content assets its config names.

It can never replace Core files or whole screens. The rule for anything an Edition needs: if it is useful to every Edition, it goes into the Core behind a Feature Switch; otherwise it goes in through an Extension Point, and if no Extension Point fits, we add one to the Core first.

Among the assets and values the Edition config names, each required of every Edition unless marked optional:

- **`wordOfTheDayFont`**, one of the Edition's own fonts, embedded like the others; the app config reads the font's family from its `name` table and passes it to the app as `extra.edition.wordOfTheDayFontFamily`, so the Edition names the font once, by its file. The app sets only the Lemma on the Word of the Day card in the Feed in it, behind the `calligraphy` Feature Switch, and every other text keeps the Edition's usual fonts. The Edition chooses it because only the Edition knows which fonts draw its letters; the Edition check refuses a font that lacks a glyph for a letter of the Edition's alphabet in either case, for the punctuation a Lemma may hold or for the Stress mark (ADR 0035), and the app config and the Edition check refuse a Core font.
- **`widgetPalette`**, the widget palette: the background and text colours of the widget's Пергамент (`parchment`) and Синій (`blue`) backgrounds; the Edition config refuses text below 4.5:1 contrast with its background (WCAG AA). Світлий and Темний come from the Edition's colour tokens, and the app config writes all of them into the widget (ADR 0026).
- **No app identity.** The app's name, scheme, bundle id, App Group, Apple Team ID, App Store Connect id, domain, icon, splash, Update channel and build profiles are the same for every Edition inside the one app (ADR 0065), so they live in the AppConfig, `app/app.json`, never in the Edition config; the Edition config refuses them. The release checks run against the AppConfig (`appReleaseProblems`) as well as the Edition config (`releaseProblems`). The Core reads neither: the app config, the backend and the workflows do.
- **`notificationSound`**, optional: a content asset, neither Decor nor a Feature Switch, a file in the Edition's `assets/` folder like the icon and the fonts, which the shell bundles and the Core only names. The config holds a plain file name ending in `.caf`, `.wav` or `.aiff`, or nothing; the Core's Edition reports that one value, and the notification plan carries it to the scheduler adapter as the sound of each notification, `{ file }`, while an Edition without one plans the system sound (ADR 0021). No second flag says "has a sound" beside the name. iOS falls back to the default sound without a word when a notification's sound is in a format it does not play or runs longer than 30 seconds, so the app config reads the file's header and stops the build instead: the container is WAV, AIFF or CAF and matches the extension, the codec is one iOS plays for notifications (linear PCM, IMA4, µLaw, aLaw) and the sound is at most 30 seconds; a WAV in WAVE_FORMAT_EXTENSIBLE, which is how ffmpeg writes 24-bit linear PCM, is read through its subformat. The header reader is used only by `apps/mobile/app.config.ts`, so it sits next to it (`apps/mobile/notification-sound.ts`) and not in `contracts`, which holds only the schema that shapes the config.

**Core fonts live in the Core.** The Core's tokens (`packages/ui/src/tokens.ts`) set the word family in Literata and the UI family in Manrope, and every Edition gets them unless its `tokens.json` names other families. The files of those families, with their licences and a README on their origin, live in `packages/ui/assets/fonts/`, next to the tokens; `packages/ui/src/fonts.ts` is the one place that names that folder (`coreFonts()`), and only build tooling imports it. An Edition's `assets/fonts/` holds only the fonts the Edition names itself: its Word of the Day font, and the files of any family its `tokens.json` sets. `app.config.ts` embeds the Core's fonts, then the Edition's own; the widget extension takes from both sets the files of the word and UI families of the Edition's tokens, so the Word of the Day font stays out of it. Font files keep their PostScript names, which iOS selects them by. `edition-folder.ts` stays the only code that knows the Edition folder's layout (ADR 0035).

## Considered Options

- **Free override of any Core file or screen per Edition**: rejected. With many Editions it turns the factory into N silent forks, where every Core change risks breaking some Edition unnoticed.
- **One calligraphic font in the Core for every Edition**: rejected. No one font draws every language's letters, and a missing glyph would fall back to another font in the middle of a Lemma.
- **Core fonts in each Edition's folder**: rejected. Every Edition would carry a copy of the Core's files, and an Edition without them would draw the Core's families in the system font.
- **A Core font package of its own**: rejected. The tokens that name the families live in `@slovo/ui`; the files beside them need no new package.
- **A Feature Switch for the notification sound**: rejected. A switch turns a Core feature on or off, and the sound is a file the Core has no behaviour for.
- **The sound as a Decor slot**: rejected. Decor is vector motifs drawn by the Core (ADR 0014); a sound is neither.
- **A flag and the sound's file name as a pair**: rejected. The pair could disagree, and the scheduler re-checked what the Core already decided. One optional value cannot.
- **The sound's header reader in `contracts`**: rejected. Its only caller is the app config, and `contracts` then holds code nothing shares.

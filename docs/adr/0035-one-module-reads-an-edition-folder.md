# One module reads an Edition folder

Until 0.7 about ten modules (the build, the id registry, the build CLI, the sourcing tool, the app config, Metro, the tests) each knew how `editions/<id>/` is laid out, and each copy could drift.

`packages/language-pack/src/edition-folder.ts` is the only code that knows where an Edition's files lie. It lists the Editions of an editions folder, opens one by its id and reads each of its JSON files checked against its contract, reporting every problem as a `BuildError` in the file it lies in. It also names where the Edition's assets, fonts, Decor files and built Language Pack lie, and checks new Words against the Edition's content the way the build does. The build, `--record`, the build CLI, the sourcing tool, the app config, Metro and the Node tests read Editions only through it, and the backend's Edition registry is meant to as well.

- **Open by id, refused by type.** `openEdition(editionsDir, id)` throws an `EditionFolderError` whose `reason` is `unknown` when no folder of that name holds an `edition.json`, and `invalid` when the config breaks its contract or carries another id than its folder's name. The id rule was the app config's alone; Metro, the build CLI and the sourcing tool now hold to it too. Reading a file throws the same error, so every caller but the build stops on the first broken file, and the build catches it per file to report every problem at once.
- **Its own entry point.** The module is exported as `@slovo/language-pack/edition`, not from the package's main entry, which loads `node:sqlite` and prints an experimental warning. The app config and Metro load it through tsx on every Expo command, as the app config already loads the other workspace packages, and it loads no SQLite. It sits beside `@slovo/language-pack/reader`, the pack reader the app uses.
- **The build reads a folder by its path.** `editionFiles(dir)` reads the Edition in any folder, whatever its name, so the build's fixtures keep their folder names. Everything that looks an Edition up goes through `openEdition`.
- **Names stay beside their schemas.** The manifest's and the id registry's file names stay in `content-manifest.ts` and `id-registry.ts`, next to the schemas and the errors that name them, and the module's table of files takes them from there. Neither leaves the package any more.
- **The Word of the Day font has every glyph.** The Edition check that the build, `--record` and `pnpm content check` run looks for `wordOfTheDayFont` (ADR 0006) among the fonts this module names, and checks that the font has a glyph for every letter of the Edition's alphabet in both cases, for the punctuation a Lemma may hold and, in an Edition that marks Stress, for the Stress mark. It names every missing character in one `BuildError` in `edition.json`, so the build refuses a font that would fall back to another in the middle of a Lemma. Opening an Edition reads no font, so the app config, Metro and the backend don't pay for the check; the app config reads only the family name of the Word of the Day font (ADR 0006).
- **A release build holds no placeholder.** `openEdition(editionsDir, id, { build: 'release' })` also refuses, as `invalid`, a `linkDomain` under a top-level domain reserved for examples (`example`, `test`, `invalid`, `localhost`, RFC 2606) and an empty `appleTeamId`, naming each field in `edition.json`. A development build, the default, keeps the placeholders, so the app runs before the owner has the real values. The contracts name what a release refuses (`releaseProblems`); this module only applies it.
- **Legal pages aside.** The module doesn't name `editions/<id>/legal/` (ADR 0049): no code reads the pages, and the GitHub Pages workflow gathers them with a shell loop before any dependency is installed. The first Node code that reads them names the folder here.
- **Not the app's runtime.** The app reads the Edition through Metro's `slovo-edition/*` modules, whose files Metro now takes from this module; it validates them at startup with the contracts as before. The notification sound's header reader stays beside the app config (ADR 0023).

## Considered Options

- **The module in `contracts`**: rejected. The app imports `contracts` at runtime, where there is no file system, and `contracts` imports nothing else of the workspace.
- **A package of its own**: rejected. One module would make a shallow package, and the Language Pack already reads Editions in Node and owns `BuildError`.
- **The module on the package's main entry**: rejected. Every Expo command would load SQLite and print its warning.
- **Metro takes a file map from the app config's `extra`**: rejected. `extra` ships in the app's manifest, and Metro would still read the locale on its own.

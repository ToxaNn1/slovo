# Remote Feature Switches turn features on and off by rules

ADR 0040 let the backend only turn a feature off: the effective value of a Feature Switch was the Edition's value and not off remotely, so nothing could switch on what an Edition hadn't shipped. That guard also made every launch of a feature a build: a feature shipped off in `edition.json` could not be turned on for a share of readers, on a date, or for one platform, and an A/B test was impossible. The owner admin (ADR 0088) now needs to turn features on and off, roll them out, schedule them and test variants, without a build (admin grill 08.11, rounds 1–14, spec #1709). This ADR supersedes ADR 0040 and amends ADR 0068 (the anonymous Analytics id becomes the Install id); ADR 0072's amendment of 0040 (the one rarity switch is `rarityCeiling`) stays in force.

**A remote Feature Switch is a rule the owner sets in the admin, evaluated on the device, that can turn a feature on as well as off; the Edition declares each feature `on`, `off` or `unavailable`, and `unavailable` is what the backend can never override.**

- **Three states in `edition.json`.** `on`: the feature is in effect unless a rule turns it off. `off`: shipped and ready, off until a rule turns it on. `unavailable`: the Edition has no content or assets for it (no Narrator Voice recordings, no Curated Collections); the admin shows no control, the backend refuses a rule for it, and no rule can turn it on. The contracts' Feature Switches schema grows from a boolean to these three values, and the Edition check (ADR 0035) keeps refusing a feature it doesn't know.
- **Dependencies stay in the Core.** The Core's Edition module holds the one list of dependencies and `isFeatureEnabled` applies it to the effective value: a feature is in effect only while every switch it depends on is, whatever the rules say. The admin shows a dependency and refuses a rule that would turn on a feature whose parent is off or unavailable.
- **Rules.** A rule names an Edition and a feature and says on or off for the readers it targets: app version (a range), platform, country, a share of readers in per cent, signed in or not, and a schedule (from, until) stored in the rule. Several rules for one feature are ordered; the first that matches decides, the Edition's state decides when none does. A rule with a field or value the app's contracts don't know is skipped, the rest of the answer holds.
- **Country** is the phone's region setting, read offline through the JavaScript locale, no native module; not the store front, not the request's IP.
- **Schedules and the clock.** The device evaluates a schedule against its own clock corrected by the offset to the `Date` header of the last rules answer, kept with the rules; a device with a wrong clock still switches on time.
- **One Install id.** The app makes one random anonymous id at first launch and keeps it on the device; a reinstall makes a new one. It is tied to no Account and no device identifier. It is the key of rollouts and variants and, while Analytics are on, the PostHog distinct id; with Analytics off it stays on the phone and serves rollouts alone. It is never sent in a switch request, a Community Counter or a Mistake Report. ADR 0068's «an anonymous id» is this id.
- **Variants.** A switch can carry two or three variants instead of on/off; the device picks one by its Install id and sends the variant as a property of its Analytics events, so the results are read in PostHog and shown in the admin. No variant assignment leaves the device as anything else; with Analytics off the variant is picked and reported nowhere.
- **Evaluated on the device.** The app fetches the rules of its Edition, keeps them in a device-only record, and evaluates them itself: offline the last rules hold, without any the Edition's states hold. The share-of-readers rule hashes the Install id salted by the rule id, so one reader stays in or out of a rollout as it grows and two rollouts of the same share pick different readers; the hash function is the spec's.
- **When it asks.** At launch, on each return to the foreground and every 2 minutes while the app is open, naming the kept ETag; 304 when nothing changed; no push. A changed effective value reopens the composition (ADR 0036) as under ADR 0040.
- **The backend obeys the rules too.** `EditionRegistry.serving` keeps reading the switches per request and holds a feature on when any rule or the Edition's state turns it on for anyone; only a feature off for everyone answers `switched-off` and its procedures `NOT_FOUND`. The backend has no device facts and asks for none.
- **Force update.** The owner sets a soft and a hard minimum app version per Edition and platform. Below the soft minimum the app shows a banner; below the hard minimum a blocking screen with the store link. The minimums travel in the same rules answer and take effect through the same fetch and reopen cycle.
- **Kill switch.** One click and a reason in the admin turns one feature off for every reader of one Edition or of every Edition at once, over every rule; it fires a Telegram alert and is logged like every other change (ADR 0088). Its scope is one feature; several features take several clicks, and the app as a whole is stopped by the hard force-update minimum.
- **Setting them.** The admin (Власник and Адмін) sets rules; every change asks for a confirmation and a reason and goes through the action log with before and after. The switch matrix shows Editions as columns; a feature on for only some Editions reads «увімкнено (2 з 3)» under «Усі Editions», and one Edition picked shows its exact state. One server command stays for when the admin is down: `pnpm switches off <edition> <feature> --reason`, the kill switch from a shell, logged the same way. `pnpm switch:off` and `switch:clear` of ADR 0040 go.

## Consequences

- The `remote_switches` table (`edition_id, feature, off, set_at`) gives way to tables of rules and of force-update minimums; `GET /v1/editions/{editionId}/switches` answers the rules and the minimums, not `{ off: [...] }`, and the shape change is a `/v1` output change per ADR 0031.
- `openRemoteSwitches` (`packages/core/src/edition/remote-switches.ts`) grows an evaluator with the device facts (version, platform, region, signed-in, Install id, corrected time) injected; `shownOf`, `useShown` and every other reader keep reading one effective value and change nothing.
- The ADR 0040 clauses that survive unchanged: ETag/304, failure keeps the last answer, per-request backend read, a cleared or changed rule keeps its history (now in the action log), `sync` apart from `account`, `account` off keeps the Session unrefreshed, `contentUpdates` off keeps the bundled pack only (now: no Patches, ADR 0090).
- ADR 0068 is amended: the PostHog adapter's «an anonymous id» is the Install id, made and kept by the app, not by PostHog; its rejection of a device id or the Account id as the analytics id stands. Community Counters and Mistake Reports still carry no id.
- The ADRs that cite 0040 (0015, 0021, 0026, 0030, 0036, 0041, 0043, 0046, 0047, 0051, 0052, 0054–0058, 0060, 0065, 0066, 0068, 0072, 0074, 0076, 0081, 0082) mostly cite the effective-value idea, which survives; a clause that says «off only» reads as «by the rules of 0089».
- Polling every 2 minutes is a new steady network cost of the app; a 304 is a few hundred bytes.
- CONTEXT.md gains Install id, Rule, Rollout, Variant, Force update, Kill switch and `unavailable`; the Feature Switch, Eligible Entry and Analytics entries are rewritten.

## Considered Options

- **Keep off-only and ship every launch in a build**: rejected. Every rollout, schedule and A/B test would be an App Store review.
- **Evaluate the rules on the backend and send each device its values**: rejected. The backend would need the device's platform, version, country and id in every request, and an offline device would have nothing to evaluate.
- **Push (silent notifications) instead of polling**: rejected. APNs is not reliable for a kill switch and adds a native path; 2-minute polling with 304 is cheap and deterministic.
- **The Account id as the rollout id**: rejected. It would exclude readers without one and tie a rollout to a person.
- **A rollout id apart from the Analytics id**: rejected. Two ids on one phone that both mean «this install» are one id with extra bookkeeping; one Install id, two uses, linked to nothing else.
- **Country from the store front or the request's IP**: rejected. The store front needs a native module and a store; the IP needs the backend in every evaluation. The region setting is offline and already in the JavaScript locale.
- **Trust the device clock for schedules**: rejected. A clock set wrong would miss a launch date; the `Date` header costs nothing.
- **Refuse the whole answer on an unknown rule field**: rejected. One new targeting field would switch every older app to the Edition's states.
- **An unsalted hash of the Install id for the share rule**: rejected. Every 10 % rollout would pick the same tenth of readers.
- **The force-update minimums in an answer of their own**: rejected. One more fetch, one more ETag, one more thing to be offline about; the rules answer already arrives every 2 minutes.
- **`serving` off for a partly-on feature**: rejected. A feature on for 20 % of readers must have its procedures; the backend cannot tell which 20 %, so on for anyone is on.
- **A hosted flag service (LaunchDarkly, PostHog flags)**: rejected. The rules must obey the Edition's `unavailable` and the Core's dependencies, live in the Deployment's Postgres, and be logged in the action log.
- **Two booleans in `edition.json` (`enabled`, `available`)**: rejected. Three named states make the illegal pair (available false, enabled true) unrepresentable.

# Content lives in Postgres and reaches the app as Patches

Content was files: `editions/<edition>/content/**` (2556 files of seven kinds), checked by `pnpm content check` and `verify` in CI (ADR 0080, 0084), built into a SQLite Language Pack whose version followed the content checksum (ADR 0011), published whole by a local `pnpm publish-pack` (ADR 0032) and opened by the app at its next launch, since a pack never changes while open (ADR 0015, 0036). Every fix was a pull request, a coordinator recording ids and a version, a 2 MB download and a relaunch. The owner wants to fix a Definition in the browser and see it in the app in minutes, let coding agents add Words through the same backend, review them afterwards and roll a bad batch back in one click, and give the site the same content without a build (admin grill 08.11, rounds 1–14, spec #1708). This ADR supersedes ADR 0032 and the whole-pack parts of ADR 0011 (manifest, checksum, `--record`); amends ADR 0015 and 0036; changes the content route of ADR 0080 and 0084.

**The Deployment's Postgres is the source of content; every save publishes on its own; the app keeps its bundled Language Pack as the offline base and applies Patches of changed records as they arrive.**

- **Seven kinds in tables.** Words, Corrections, Idioms, Synonym Rows, Tips, Curated Collections and Crossword days are imported from the repo files into Postgres, one table per kind, partitioned by `edition_id` (ADR 0030), with the ids they have today: Entry ids never change meaning (ADR 0010). Categories, with their `description` and `tone` (ADR 0081), stay in `edition.json`: they are Edition config, not content. UI strings, legal pages and assets stay in the repo and ship in the build and the image. Recordings stay app assets (ADR 0083).
- **The database issues ids.** A new record gets its id from a sequence per kind and Edition; `content/ids.json` (ADR 0010) ends with the files, its last values seeding the sequences.
- **Every save publishes.** A save in the admin, or a write by an Агент token, is live for the app, the site and the next pack build at once: no batching, no pull request, no coordinator. The content version is a number the database raises on every publish, per Edition, and only grows; each record also carries its own version. Two different contents never share a version (ADR 0011's rule, without its manifest). A rollback is a publish too, so the version grows.
- **Checks on save, quotes in the background.** The fast rules of `pnpm content check` (schema, stress, ids, cross-references, dependencies) run on the backend at every save and refuse a record that fails, with the reasons; the CLI shows them. The quote check of ADR 0084, slow and network-bound, runs as a background job (the Cron service of ADR 0088) over records added or changed since its last run, keeps its sourcing cache in a Postgres table, and flags a failing record in the Content queue, like an agent's flag.
- **One package of content rules.** The rules live in `packages/content-rules`, a language-agnostic package that imports only contracts and Zod: the Language Pack build and the backend's save check call the same `checkContentSet` and `checkRecord`, so a record the backend takes is one the build takes.
- **Version check per record.** An edit names the record version it saw; a save over a newer version is refused with a diff and asks again.
- **Retire, never delete.** A record leaves the app as Retired (Retired Word, Retired Correction, Retired Idiom); rows are never deleted.
- **Needs new recording.** A change to a Word's text or stress marks it «потребує нового запису»; Pronunciation hides for that Word until a Recording for the new text ships (ADR 0083).
- **Patches only.** The app asks, at launch, on each return to the foreground and every 15 minutes while open, for the records changed since the content version it holds, and applies them at once over its open pack. A device far behind gets one bigger Patch of everything changed since its version; there is no whole-pack path. A Patch carries a format number; an app refuses a Patch of a format newer than it reads and keeps what it has, as `PACK_FORMAT` did for packs. An Entry on screen keeps its old text until the reader moves on. Offline, the next open with network catches up.
- **A pack changes under its open reader.** «A pack never changes while open» gives way to: a Patch is written into the open pack inside one transaction, so a reader sees the records before it or after it, never half of them, and the Entries module reads the live Entries per Patch, not once per session (amends ADR 0015). The shell still opens the pack once per app run (ADR 0036); it no longer keeps a newer pack beside the bundled one, and a Patch is a change under the one reader, not a reopening.
- **The bundled pack is built from the database.** At EAS build time the build fetches a snapshot of the Edition's content from the backend API and builds the SQLite Language Pack from it, stamped with the content version of the snapshot, so a fresh install and an offline device have every Entry without network and the first Patch is small. `contentUpdates` off means no Patches, the bundled pack alone (ADR 0089).
- **The repo files go.** `editions/*/content/**`, `ids.json`, `manifest.json` and `targets.json` stay read-only after the import until the first build whose pack came from the database ships; then they are deleted in one change with `pnpm build:pack --record`, `publish-pack` and `tools/content`'s file readers.
- **The site** (`apps/site`, Astro on Cloudflare Pages) renders on the server per visit: Pages asks the backend API for Слово дня and the Entries, cached about 5 minutes, so the browser calls no API and no CORS opens; no build on a content change. Слово дня is chosen by the backend by the Kyiv date, so the site and the app name the same Word.
- **Agents write through the backend.** `pnpm content add|edit|flag <edition>` (an MCP server later) calls the admin API with the Агент token. One CLI run is one batch; the batch publishes at once and lands in the Content queue (Черга контенту) marked «не перевірено». A content wave is such a run per implementer: no version bump, no recording of ids or manifest, no PR; this replaces the wave route of ADR 0080. The owner reviews afterwards: accepts, edits, or «Відкотити пачку», which reverts the whole batch, new records to Retired and edits to their previous versions, skipping a record anyone changed after the batch and listing the skipped ones. A batch that changes more records than a set limit (200 for a start) fires a Telegram alert. An agent can also flag a record with an explanation; the owner accepts or rejects the flag in the admin.
- **The content editor** belongs to the admin (ADR 0088, spec #1709): every kind, search and filters, every field editable, add, retire; a save is one click with an optional reason, and every write is in the action log with before and after.
- **Order.** The «content in the database and Patches» spec (#1708) comes before the admin's content editor; other admin sections may go in parallel.

## Consequences

- ADR 0032 is superseded: whole-pack Content updates, `pnpm publish-pack`, the `content_packs` table, the `not-recorded` and manifest checksum refusals and the once-a-day check go. ADR 0011's manifest, checksum and `--record` go with them; its one rule, two contents never share a version, lives on in the database counter. `content.latest` and `content.download` stay in `/v1` for apps in the field (ADR 0031): `latest` answers no pack to an Edition it serves, `download` answers NOT_FOUND.
- ADR 0080's route for agent content, pull request, `content check`, CI, a coordinator's `build:pack --record`, no longer applies to content: the fast gates run on the backend at save, the quote check of ADR 0084 as a background job; CI keeps `content check` and `verify` only until the files go. `docs/agents/content-wave.md` is rewritten around `pnpm content add`.
- Repo docs change: CLAUDE.md «An Edition is configuration plus content and assets» becomes configuration and assets in the repo, content in Postgres; `docs/agents/map.md` (`editions/<edition>` content, `tools/content`); `docs/deploy.md` lines on the publish command.
- The backend gains a snapshot endpoint the EAS build reads, and the build profile gains the fetch; a build with the backend down fails rather than ships an old pack. The endpoint's access (a public read of published content or a build token) and the exact command the build profile runs are the spec's.
- The Entries module (ADR 0015) and the pack reader gain a write path for Patches and lose the once-per-session read; a Patch with a Category new to the Mix joins it per ADR 0019, 0033.
- Favorites, Collections, History, Hidden Entries and the Mix carry over, since ids never change (ADR 0010).
- A Word changed in text or stress loses Pronunciation until the next build with a new Recording: content is minutes away, Recordings a build away.
- The Collection Link web page (`pack-entries.ts`) reads Entries from the tables, not the stored pack.
- CONTEXT.md: Content update, Language Pack, Edition and the Retired entries are rewritten; Patch, Content version, Content queue, Batch and Needs new recording are added.

## Considered Options

- **Keep files in the repo and let the admin open pull requests**: rejected. A fix would still wait for CI, a review and a build; two writers (admin, agent) through git would conflict; the owner asked for minutes, not a pipeline.
- **Whole packs on every save** (ADR 0032 kept, published by the admin): rejected. Every save would push 2 MB to every device and open at the next launch; the owner asked for the Entry to update on screen.
- **A whole pack as the catch-up for a device far behind**: rejected. Two delivery paths, two formats and two tests for one result; a big Patch is the same records in the same shape.
- **Patches as deltas of fields**: not chosen; the unit of a Patch is a changed record, whole, so the device replaces a row and merges nothing. ADR 0032 rejected deltas for fear of merge logic; a whole record has none.
- **Apply a Patch by reopening the pack**: rejected. Reopening would run every gate of ADR 0036 for a one-word fix; a transaction under the open reader changes the rows and nothing else.
- **Build the bundled pack from the repo files or from a Postgres dump**: rejected. The files are going, and a dump needs database access on the EAS builder; the API snapshot is the same read the Patches use.
- **Approve before publish for agent batches**: changed by the owner (round 10). Agents publish at once; the owner reviews after, with batch rollback as the safeguard.
- **Roll back over later edits**: rejected (round 14). A record anyone changed after the batch is the newer truth; the rollback skips it and lists it.
- **The site fetching content in the browser or at build time**: rejected (round 14). A browser fetch needs CORS and shows a blank first paint; a build fetch lags until the next build. Server rendering on Pages with a 5-minute cache does neither.
- **The quote check's sourcing cache on the Railway disk or in object storage**: rejected (round 14). A Cron run starts on a fresh container; the Postgres the job already reads keeps the cache across runs.
- **Keep the files as a mirror the backend writes back**: rejected. Two sources of truth; git would hold a copy nobody reads. Deleted once the database-built pack has shipped.
- **Delete rows**: rejected. Retire keeps History, Favorites and Collections meaningful (ADR 0010).
- **Content in object storage or a headless CMS**: rejected. The rules (ids, Retired, versions, the Content queue, roles) are the product's own and belong in the Deployment's Postgres under the server Core.

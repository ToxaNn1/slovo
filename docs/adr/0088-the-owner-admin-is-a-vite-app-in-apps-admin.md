# The owner admin is a Vite app in `apps/admin`, served by the backend at `/admin`

ADR 0069 gave the owner a minimal admin: server-rendered Hono pages at `/admin`, one Account named by `OWNER_EMAIL`, remote switches that only turn off, summed counters and the Mistake Report inbox. The owner's idea menu (08.11, 53 picks) asks for far more: content edited in the browser, switches that turn on by rules, analytics and quality read from PostHog, Sentry and GitHub, Telegram alerts, a second person (an admin) and coding agents writing content through the same backend. Pages without client script cannot carry that, and one Account with an allow-list in an environment variable cannot carry roles. The admin grill of 08.11 (rounds 1–14, spec #1709) decided an app of its own, built so that it could leave the monorepo in about a day if it ever has to. This ADR supersedes ADR 0069.

**The owner admin is a Vite app, `apps/admin`, that imports only `@slovo/contracts`, talks to the backend over HTTP alone, and is served built by the backend at `/admin` on the Deployment.**

- **Stack.** Vite, React, TanStack Router with file routes, TanStack Query; Tailwind 4 and shadcn/ui, charts from shadcn. Light and dark. The UI is in Ukrainian and uses glossary terms (Game, Review, Pronunciation), not a design's words. Desktop first; the phone gets Огляд and the kill switch.
- **The design is the look only.** «SLOVO Admin v4» sets styles, fonts, blocks, layout and both Themes. Every function comes from the owner's decisions; whatever the design shows beyond them (a «частково» switch state, a platform scope on the kill switch, reason chips, a read-only restore mode, per-event alert mutes, another person's sessions signed out, a recovery-code download and the like) is not built. Where the design lacks a decided function, the function is built from the decisions in the design's style.
- **The boundary.** The admin reaches no other workspace package than `@slovo/contracts`, and no backend code: everything it knows about the backend is the contracts' admin API, called over HTTP. A dependency-cruiser rule enforces both (the pattern of ADR 0086's site rules). React and `react-dom` stay the versions the Expo SDK sets, as the site's do.
- **Served by the backend.** The backend serves the built admin at `/admin` on Railway, same origin as the API, so the admin needs no CORS and its cookie stays first-party. CI builds `apps/admin` into the container image.
- **Seven sections** behind a sidebar, with a global Edition filter («Усі Editions» or one) and period filter kept across sections: Огляд, Контент, Свічі, Аналітика, Якість, Розробка, Безпека. Магазини (App Store Connect, Google Play) is deferred whole. Edition card, themes and levels are read-only: `edition.json` stays in the repo and is edited through pull requests; only content is edited in the admin (ADR 0090). Mistake Reports (ADR 0056) land in the Content queue (Черга контенту) under Контент, next to the agent batches; the Community Counters sums (ADR 0060, 0068) are a view of Аналітика. In Якість the period is capped at 30 days, since Sentry keeps 30, with the hint «Sentry зберігає дані 30 днів».
- **Admin users, apart from Accounts.** An admin user is a row of its own table, not an Account: an email, a role, TOTP, and sessions of its own carried in an `HttpOnly`, `Secure`, `SameSite=Strict` cookie scoped to `/admin`. Sign-in is an emailed code plus TOTP; passkeys come later. The code lives 10 minutes; three failed attempts on a code or on TOTP block that email for 15 minutes. Setting up TOTP gives ten one-time recovery codes, shown once; a code signs in instead of TOTP and is spent. A session ends after 8 hours idle and 30 days at most; «Вийти всюди» ends every session of the user.
- **CSRF.** `SameSite=Strict` plus a custom request header on every write (`X-Slovo-Admin: 1`); the backend refuses a write without it. No token to store or rotate.
- **Three roles.** Власник does everything. Адмін does everything but the Безпека section (people, agent tokens, the action log): edits, approves and publishes content, changes switches, fires the kill switch and the force update. Агент is a service token for coding agents, not a person: one token per agent, named, issued and revoked by a Власник in Безпека; it writes content through the backend API (`pnpm content add|edit|flag`, an MCP server later, ADR 0090) and nothing else, and the action log names the agent.
- **The first Власник and the off state.** A server command, `pnpm admin owner add <email>`, run against the Deployment's database, creates a Власник; further people are added in Безпека. The admin is on while at least one Власник exists; without one `/admin` and the admin API answer 404. `OWNER_EMAIL` goes.
- **Every change asks for a confirmation and a reason.** Switches on and off, the kill switch, the force update, batch rollbacks, roles, agent tokens and alert thresholds take a required reason before they apply; the kill switch takes one click and the reason. Two exceptions: an Entry save in the content editor saves in one click with an optional reason, and ticking an owner check takes none.
- **The action log.** Every write through the admin API, the server commands included, is appended to an action log, kept forever and never edited: who (admin user, Агент token or command), when, what, the value before and after, and the reason. Read in Безпека, filtered by Edition.
- **Reads from the services that have the data.** The backend reads analytics and performance from PostHog's and Sentry's APIs behind ports of the server Core, cached with a per-source freshness, and keeps no event store of its own; it shows aggregates only, never a list of people. GitHub's current state (pull requests, checks) comes through a read-only fine-grained token, cached; history (coverage, flaky tests, CI speed) is pushed to the backend by CI. Version progress reads GitHub milestones, tags and releases, and the latest EAS builds through the EAS GraphQL API with a read token; the first ticket of that stage verifies the API, and the admin says «EAS недоступний» where it fails.
- **Secrets.** The GitHub and EAS tokens and the PostHog, Sentry and Telegram secrets are environment variables of the Deployment (ADR 0063), listed in `docs/deploy.md`; no secrets table.
- **Background jobs** run as a Railway Cron service on the backend image: the daily Telegram digest (09:00 Kyiv), the alerts to a bot that talks to the owner alone, with thresholds set in the admin, and the quote check of ADR 0090. The alerts and their default thresholds: crash-free sessions below 99.5 % over 24 hours; a new Sentry issue with 10 or more events in an hour; any red CI on `main`; API 5xx above 2 % over 15 minutes; a backend down; a kill switch fired; one batch changing more than 200 records (ADR 0090).
- **Owner checks** move from `docs/owner-checks.md` into the database, per version: the owner ticks them in the admin, agents add them through a command.
- **Development.** `pnpm dev:admin` runs Vite, the backend and the Docker Postgres of `compose.yaml`, no Metro; Vite proxies the API to the local backend, so no CORS code exists anywhere. `pnpm dev:admin --mock` runs Vite alone against MSW fixtures generated from the contracts, no Docker. Neither can point at the Deployment.
- **Order of building.** 1 skeleton, sign-in, roles, action log, dev commands; 2 switches (ADR 0089); 3 Контент, the content editor and the Content queue, after the content spec of ADR 0090 (#1708); 4 Аналітика and Якість; 5 Розробка; 6 Telegram, alerts and the rest. Other sections may go in parallel with 3.

## Consequences

- ADR 0069 is superseded whole: `apps/backend/src/admin/admin-routes.ts`, the `/admin` Hono pages and `OWNER_EMAIL` are removed in the same change. `docs/deploy.md` loses the `OWNER_EMAIL` row and gains the `pnpm admin owner add` step and the secrets rows.
- The contracts gain an admin API namespace; the backend gains admin-user, session, recovery-code, agent-token, action-log and alert-threshold tables and an authenticator for them, apart from better-auth's Account tables (ADR 0030).
- The Mistake Report inbox with Resolve (ADR 0056) becomes part of the Content queue; the Community Counters sums move to Аналітика; no list of Accounts, as before.
- Two sign-in systems live on the backend: Accounts for readers, admin users for the admin. They share nothing but the mailer and the rate-limit port.
- A new Deployment has no admin until the owner runs the command once; the command is the only way in without an existing Власник.
- `docs/agents/map.md` gains `apps/admin`; CI gains its lint, typecheck, tests and build; dependency-cruiser gains the boundary rules.
- CONTEXT.md gains Admin user, the roles Власник, Адмін and Агент, Action log, Owner check, Content queue and the admin sections; Account lists «admin user» under _Avoid_.

## Considered Options

- **Keep the Hono pages and grow them**: rejected. Content editing, charts and diffs need client state; pages without script would grow a second, worse frontend.
- **A repository of its own for the admin**: rejected for now. It would double CI, ownership checks and Dependabot, and could not import the contracts without publishing them. The contracts-only, HTTP-only boundary keeps the move to about a day if it is ever wanted.
- **A hosted dashboard (Retool, Metabase and the like)**: rejected. Content editing with glossary-aware forms, the Content queue and the action log are the product's own rules; a hosted tool would hold them outside the repo.
- **A role column on Accounts**: rejected. Readers and admins must not share a sign-in path or a table; an Account compromise must never open the admin.
- **An own event store for analytics**: rejected. PostHog and Sentry already hold the events; the admin shows them.
- **Expo Router web for the admin**: rejected. The admin shares no screen with the app and must not pull React Native; Vite builds it without Metro.
- **An environment variable or a seed for the first Власник**: rejected. A variable is the `OWNER_EMAIL` allow-list again; a seed runs on every deploy. One command, run once, leaves a row and a log entry.
- **A CSRF token**: rejected. Same origin, a strict cookie and a header the browser sends only from the admin's own script are enough; a token adds state for nothing.
- **CORS for localhost in development**: rejected. A Vite proxy gives the same result with no CORS code that could reach production.
- **One shared Агент token**: rejected. The action log must name the agent, and one leaked token must not revoke them all.
- **A secrets table**: rejected. Secrets edited in the admin would be one more thing the admin can leak; Railway's variables already exist (ADR 0063).
- **A reason on every write without exception**: changed by the owner (round 13). A content fix is many small saves a day; the action log keeps before and after anyway, so the reason is optional there and absent on an owner-check tick.
- **Building what the design shows**: rejected. The design is a direction for the look; a feature the owner never decided is not built because a mock-up drew it.

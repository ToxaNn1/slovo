# Content updates ship whole Language Packs

A Content update is a newer Language Pack of the Edition that the app downloads by itself, without an Account, and opens from the next launch, so a new Word, a corrected Definition or a Retired Word reaches a reader without an App Store build. It is the Edition's whole Language Pack of a newer content version, the file `pnpm build:pack` builds, never a delta of Entries: the app already opens packs, so there is no merge logic on the device. The cost is downloading the whole pack (about 2 MB) for any change, at most once a day.

- **The pack format.** The pack's metadata records a pack format beside the content version and the content checksum. It rises whenever a pack carries something an older app can't read: a layout change, or a new value of a closed set in the contracts, such as a Correction Type, since the app checks what it reads against the contracts and refuses an unknown value. The app asks for the newest pack of the format it reads, and the backend answers with the newest pack published in that format, or none, so a pack in a new format never reaches an app that can't read it. The build writes, and the app reads, the one constant `PACK_FORMAT` of `@slovo/language-pack`, now 3 (format 1's layout plus the Idiom tables `idioms`, `idiom_definitions` and `idiom_examples`, the Entry kind `'idiom'`, the new Correction Types and the Word's nullable region). The app reads no older format: the bundled pack is the current format, so no older-format pack is newer than it.
- **Two checksums.** The content checksum stays as ADR 0011 defines it. Publishing also records the SHA-256 of the pack file, which `content.latest` announces with its size and the app checks after downloading; a download that fails the check is thrown away.
- **Storage in Postgres.** Each published pack is one row of `content_packs` with the bytes of the file, partitioned by `edition_id` (ADR 0030). A row is never updated: a content version, once published, is immutable.
- **One local publish command.** `pnpm publish:pack <edition-id>` publishes the Edition's built pack. The rules live in the server Core's `content` domain: it refuses a pack of an Edition the backend doesn't find, a pack whose content checksum isn't the one the Edition's `content/manifest.json` records, and a content version not higher than one already published for the Edition in any pack format. So two different packs never share a content version (ADR 0011). The Drizzle adapter of the `ContentPackStore` port runs the check and the insert in one transaction under a lock per Edition; the server Core never sees the transaction. Publishing from CI waits for a deployed server (0.9).
- **Serving the file.** `content.download` answers an Edition's pack file by content version. The server Core reads it from the `ContentPackStore` once and keeps it in memory, and downloads that arrive during the read wait for that one read. The answer carries the file's SHA-256 as its ETag and `Cache-Control: immutable`; a matching `If-None-Match` gets 304. An Edition with the `contentUpdates` Feature Switch off is `NOT_FOUND` for `content.latest` and `content.download`, as an Edition the backend doesn't find.
- **Opening at the next launch.** A downloaded pack never opens under the reader's finger: the pack never changes while it is open (ADR 0015). The Language Pack's opening (ADR 0036) runs `openLaunchPack` (`apps/mobile/src/content-update/launch-pack.ts`): it opens the bundled pack first, then, when content updates are on, the Content update module's `openKept(open)` decides. When a kept pack is newer than the bundled one, it calls the shell's `open` with its version (through `openPack`, so a pack of another Edition is refused) and the shell closes the bundled pack; otherwise it forgets any other kept pack and the bundled one stays, so an App Store update with newer content never goes back to an older download. When `open` rejects or the kept version can't be read, the module forgets the kept pack and rejects, the shell reports it, and the bundled pack stays open; the next due check downloads again. The lifecycle adapter asks the module to check at launch and on each return to the foreground; the module limits checks to one a day.
- **Content updates are on** only when the Edition's `contentUpdates` Feature Switch is on and the native-modules check reports `expo-file-system`; otherwise, or when the module fails to open, the bundled pack opens alone.
- **Pack files.** The `PackFiles` adapter keeps each downloaded pack as its own file named by its content version in `content-update/` in the app's documents directory, with a record of the kept one's version. Keeping a newer pack writes a new file and never touches the open one. At launch, before a kept pack opens, `throwAwayAllBut(version)` throws away every pack file but the one about to open, so an open pack's file is never thrown away; the bundled pack's file lies elsewhere. The file comes from the contract's client as a `Blob`, read with `FileReader`, since React Native's `Blob` has no `arrayBuffer()`.

Entry ids never change meaning (ADR 0010), so Favorites, Collections, History, Hidden Entries and the Mix carry over to the new pack, and a Category new in the pack joins a Mix that follows the Edition's default (ADR 0019, 0033).

## Considered Options

- **Deltas of Entries**: rejected. The app would need merge logic for every kind of change, and a broken merge would corrupt the content a reader has.
- **Packs in object storage**: rejected for now. One backend instance and packs of a few megabytes need none.
- **Overwrite a published version**: rejected. Two devices could hold different packs under one content version (ADR 0011).
- **The rules of publishing in the adapter**: rejected. The server Core holds the backend's rules (ADR 0030); the adapter only keeps them atomic.
- **Copy the kept pack over the bundled one's file at launch**: rejected. The bundled pack is copied into place on every launch, and a 2 MB copy would lengthen the splash.
- **Content updates without the file system, keeping the pack in memory**: rejected. A pack that opens from the next launch must outlive the app run.
- **The shell forgets a kept pack that fails to open**: rejected. Half of the rule would live in the shell, and a shell that skipped the call would keep a pack that fails at every launch.
- **Keep the old format and let an older app skip an Entry it can't read**: rejected. An app already in the App Store refuses the Entry at its contract check, and skipping it would need a new app first.
- **The app also reads older formats**: rejected. No older-format pack is newer than the bundled one, so it would keep alive a code path no pack needs.

# The shell opens each resource once through one module and draws every screen over it open

Until 0.7 the shell had four ways to open something once per app run and retry or fall back, two separate in-memory fallbacks for the user state, and screens that read a Core module through a hook returning a stand-in until the composition opened, so each route told loading from empty and drew its own error state.

The shell has one opening module, `apps/mobile/src/opening.ts`:

- **`openOnce(open, { onError, fallback })`** opens a resource on its first read and shares it for the app run: loading, then ready with the value, or failed with a retry that opens it again for every screen. A failure is reported; with a fallback the opening is ready with the fallback instead. `opened()` gives the value once ready, so one opening can wait for another. The Language Pack, the user state, the settings, the composition, the Account, Sync and the remote switches open through it. Only the user state has an in-memory fallback; the settings fall back to `Settings.defaults` (the Edition's defaults and the Core's own for settings no Edition sets) over that same user state.
- **`reopen()`** opens the value again while the opening stays ready with the old one, so every gate keeps drawing; once open, the opening is ready with the new value and tells its subscribers once. A failed reopen is reported and keeps the old value, with no fallback. Reopens run in turn; one asked while the opening still opens waits and then opens again. An opening not read yet, or failed, has nothing to reopen. Sync reopens the settings and the composition after it changes the user state, and the remote Feature Switches reopen the composition when an effective value changes (ADR 0040). A reopen is not a launch: whoever reopens does what the launch did, such as the notification plan and the Widget Snapshot.
- **`useSubscribed(source, snapshot)`** binds a screen to anything with `subscribe` and a snapshot that stays one value until the source changes (ADR 0016). Its plain part, `bind`, gives `useSyncExternalStore` one `subscribe` per source, so a reopened composition's modules are followed and the old ones left. The Vitest tests drive `openOnce` and `bind`, the module's seams without React.
- **The Shell** (`apps/mobile/src/shell-value.tsx`) is one value with every opening of the app run as a field: the user state, the settings, the remote switches, the Language Pack, the composition, the Account and Sync (undefined when the Edition has none), Mistake Reports, the reads and the sending of the Community Counters, and the device's Share Card capture. No opening is a module-level value: each module exports a function that builds its opening over the openings it waits for, and `createShell()` (`apps/mobile/src/shell/app-shell.ts`) builds them all once, over one user state; nothing opens until something reads it. The root layout hands the app run's Shell down with `ShellProvider`, and a screen or hook reads it with `useShell()`; `useComposition()`, `useEditionInEffect()` and `useEntries()` read their openings from it. The links from outside the app, which Expo Router resolves outside React, read the same Shell from `app-shell.ts`. A Jest test draws a route under `ShellProvider` with a Shell of its own, `testShell(overrides)` (`apps/mobile/src/shell/test-support.ts`): the openings it gives, already open (`opened(value)`), and the rest over the Core's fakes, so a route renders over a real composition and no test stubs an opening by its file path.
- **`Opened`** (`apps/mobile/src/opened.tsx`) draws the Feed's loading state while its opening opens, the error state with «Спробувати ще» when it fails, and its children once open. The root layout puts the composition's gate inside the Language Pack's, around the tabs and the onboarding, so every screen draws over an open composition; `useComposition()` gives it without `undefined`. The settings open before both and apart (ADR 0016, 0018), since the gate's screens need the Theme.

What a screen keeps in React state over a module of the old value must not outlive a reopen: the settings provider keeps the reader's last change only over the settings it was made in, and a reopened Feed opens on the card it kept for the reader.

## Each opening

- **The Language Pack** is copied into place and opened with expo-sqlite's `importDatabaseFromAssetAsync` and `openDatabaseAsync`. Its opening is ready with the reader of the pack the app run opened, the bundled one or a newer one a Content update kept (ADR 0032), and with the Content update module when content updates are on. A kept pack that fails to open is forgotten and the bundled one opens; only a failure of the bundled pack fails the opening, and the pack is closed so a retry copies it again.
- **The composition** reads the rows of the kept Entries as it opens (ADR 0015). A failed read fails the whole opening, so the reader sees the full-screen error state and the retry reads every row anew; nothing opens with lists short of the Entries whose read failed (owner decision 22.10). A composition failure fills the screen without the tab bar, since the app can't show any Entry.
- **The Account** opens apart (ADR 0037), and the app never waits for it. Its gate is not in the root layout: the SLOVO ID screen's route puts its content under `Opened` with the Account's opening, and its children read it with `useOpened`. The «SLOVO ID» row of Settings needs no gate: it reads the opening and the Account's state with `useSubscribed` and shows no value until open. The onboarding's SLOVO ID step opens the same screen inside the onboarding, so its back link returns to the step; the step stays on screen until the Account is open, and a tap on «Увійти через SLOVO ID» starts the opening or retries a failed one. The gate's loading and error states never cover the onboarding. An Edition without the Account has neither the row nor the screen.

## The app's moments

`reportForeground` (`apps/mobile/src/foreground/foreground-reports.ts`) is the one report of the app's moments: `launch`, `return`, `new-day` and `background`. A listener names its opening and hears `launch` once that opening is open, after any retries, and every moment after, with what the opening holds at that moment. The lifecycle adapter is `listen(shell, device)` (`apps/mobile/src/shell/lifecycle.tsx`), a plain function over the Shell and what it reaches on the device (the clock, the app state, the Widget Snapshot's writer and the Spotlight index), which returns the call that stops it; its component, drawn outside the gates so no listener waits for another's opening, runs it over the Shell it is drawn under. The composition acts on `return` and `new-day`, the Widget Snapshot's write on `launch` and `background`, the Content update check and the Account's refresh on `launch` and `return`. The Core keeps its limits: one Content update check a day, one Session check an hour. The Feed, and the Game screen that pauses a timed Game in the background, read whether the app is in the foreground through `useInForeground`, a state rather than a moment, and the «SLOVO ID» row asks the Account to refresh each time Settings opens.

## Considered Options

- **A gate in every route**: rejected. Each route would still name its opening and error state, and the onboarding and the lifecycle adapter would need gates of their own.
- **A stand-in value until open, for any source**: rejected. Every route still tells loading from empty, and every change guards against a module not open.
- **Keep expo-sqlite's provider for the Language Pack**: rejected. Its opening lives in React state, so the composition could not wait for the pack outside React.
- **The Account's gate in the root layout**: rejected. A slow or failed Keychain read would hold up the Feed for an Account the reader may never use.
- **Show the «SLOVO ID» row only once the Account is open**: rejected. A failed opening would hide the row and the retry with it.
- **Show the loading state while reopening, or a new opening per reopen**: rejected. The first unmounts the navigation stack and the open Entry; the second makes every reader learn which opening is current.
- **Fall back on a failed reopen**: rejected. The old value, open a moment ago, shows the reader more than the defaults.
- **Every listener acts on every moment, or the background is any move out of the foreground**: rejected. A `resume` at launch plans the notifications and the Game twice, and pulling down the control centre would write the Widget Snapshot each time.
- **Open the composition without the rows that failed to read, or try the read again first**: rejected. Lists would open short with no reason shown, and a read of a pack on the device seldom passes by itself.
- **Each opening a module-level value, imported where it is read**: rejected. The lifecycle adapter imported nine of them and wired them by hand, and a screen test had to stub each by its file path, so a test broke when a folder was renamed and few tests drew a route over the real gate.

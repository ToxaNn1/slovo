# One Core composition opens the Feed and the user's words together

The Feed, Favorites, Collections, History, Hidden Entries and the Mix depend on each other. Hiding an Entry or changing the Mix changes which Entries are eligible, so the Cycle reads them again and the Feed drops the cards that are no longer eligible. An Entry that becomes Seen joins History in the same write. A heart tapped in the Feed changes the counts on the Saved tab.

The Core opens all of them in one composition once the Language Pack is open, over one Entries module, one Cycle and the stored user state, and makes every link inside it. Each feature tells its subscribers when it changes, as the Feed does (ADR 0016), so a shell subscribes to what it draws and holds no rule between features. Tests drive the composition, not the features one by one.

The settings that style the Language Pack's own loading and error screens (Theme, font size, Vibration) open before the pack and stay apart from the composition.

**The modules link through named subjects the composition owns.** A module returns its module only: `openFeed` the Feed, `openNotifications` the Notifications, and so on, never a callback for the composition to route. What one module must know of another's change travels through a subject, a typed `Subject<T>` with `publish` and `subscribe` in the Core (`subject.ts`), which the composition creates before any module opens and hands to the modules that publish or follow it. Their names are the facts: `eligibility` (the Hidden Entries and the Mix publish it; the Cycle reads the eligible Entries again, then the plan, the Feed and the Game Modes on offer follow), `seen` (the Feed publishes the Entry that became Seen; the plan follows a Reserved Word), and the day change's `dayStarted`, `opened`, `dayTurned` and `returned`, which `createDayChange` alone publishes, in its fixed order (ADR 0022). A module's interface to the composition is its parameter list: it names each subject it publishes or follows with a `Pick` of the one side it uses, so a reader of the Feed knows what reaches it without reading the composition, and a module added later follows a subject by subscribing, with no edit to the composition's body. A subject's listeners run one after the other, in the order they subscribed, and a publisher that awaits `publish` knows every listener followed, or none after the one that failed, so the day change still leaves a day whose turn failed to the next report. The order the listeners of one subject follow in is the order the composition opens the modules in; the composition says so beside the opens, and a test of the day change pins it. What is not a change but a question stays a method of the module's interface: the Community Counters' `countMark` and `countSaved`, the changes to write with a mark or a Favorite, and `nextMorning` of the Notifications.

**A composition a reopen replaced closes.** The shell reopens the composition over the same user state (ADR 0036). A composition has `close()`: from then on it writes nothing to the user state, hands the device no plan, and the Game tries no planning of its offers again; its modules stay readable and their changes stay in memory only. It closes at the ports it was given (the user state's `write`, the scheduler's `replacePlan`, the `schedule` of the Game's tries), so no module needs a rule of its own and a module added later is closed too. `close()` resolves once the writes and plans under way end, and never rejects. The shell's opening takes a `close` with the value a reopen replaced and calls it after telling its subscribers of the new value, so React cleanups that run afterwards find the old composition closed. Work the old composition started before closing still ends as it would; reopens follow a sync or a remote switch check, both waiting on the network, so that work has ended by then.

**The composition takes the whole Edition.** `openComposition` takes the `Edition` that `loadEdition` gives, the one interface of the Edition the Core owns, and hands it on to each module. A module keeps its own `Pick` of the Edition as its interface, so the seam between the composition and a module stays narrow and local: a module that reads one more field widens its `Pick` alone, and the composition changes nowhere. A default of an Edition field lives in the Edition's config schema, which `loadEdition` applies, or in the module that owns the field, never in the composition: the composition is an adapter between the Edition and the modules, not a second Edition. Tests build their Edition with one `testEdition(overrides)`, loaded from a config in the shape of a real Edition's, so a test says only what it changes.

An undo toast may outlive the composition it came from, so «Скасувати» undoes in the composition open at the tap: a hide's undo is an unhide of what it changed, and a restore's undo hides the Entry again at the time it was hidden (`hiddenAt`, which an unhide returns).

## Considered Options

- **Separate Core modules that the shell connects**, such as a call to the Feed after each hide: rejected. The links decide what the reader may see next, yet they would live in untested React code.
- **A stream of user-state changes that each module subscribes to**: rejected. The links become implicit, the order of writes is hard to reason about, and tests would still assemble several modules to see one behaviour. A subject differs: it names one fact of the domain, and only the module that owns the fact publishes it.
- **Settings inside the composition**: rejected. The Theme is needed before the Language Pack opens.
- **A hand-written ordered chain in the composition** (`eligibilityChanged`, and the day change given five callbacks), the decision in force until architecture review 7: replaced. Six modules returned plumbing for the composition to route, the composition held forward references TypeScript could not check, with comments to say they were safe, and understanding «an Entry became ineligible» meant reading six modules and the composition.
- **One typed event map** (`events.publish('seen', id)`, `events.on('dayTurned', …)`) in place of separate subjects: rejected. Every module would take the whole map and name its events by key inside its body, so the seam between a module and the composition would be as wide as the map, and a module's dependencies would hide in its code instead of its parameters.
- **The day change as a subject's listener too**, with the Active Day and the morning Word among the reactions: rejected. Its steps are unlike and ordered (ADR 0022): the morning Word before anything reads the day, the Knowledge Marks before the opened Word's card is built, the Active Day in that Word's write, the plan and the Feed after it. They stay one explicit sequence in `createDayChange`, which publishes a subject at each point the other modules follow.
- **Close the old composition before the new one opens**: rejected. Every heart, hide or mark tapped while the new one opens would be lost.
- **A `closed` check in each module**: rejected. Each module would carry the same rule, and a write path missed or added later would stay open.
- **An undo after a reopen does nothing, or the reopen takes the toast away**: rejected by the owner.
- **The composition's `edition` parameter as the intersection of every module's `Pick`, with defaults for the fields a test may leave out** (architecture review 7): rejected. The intersection grew with every module and made the composition the deepest reader of the Edition, its defaults hid in call-site objects, and every Core test stubbed the Edition again, each knowing the switches and Mix keys of the modules it did not test.

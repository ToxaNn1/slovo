# «Сервіси» is the eighth Owner admin section, a Власник only

SLOVO runs on about a dozen outside Services, and the owner had no single place that shows them (spec #1949). ADR 0088 gave the Owner admin seven sections, none for the Services themselves.

**An eighth section, «Сервіси», a Власник only.** It comes after Безпека in the sidebar and, like Безпека, an Адмін neither sees it nor opens it, and an Агент token is refused: every `/v1/admin/services.*` procedure answers `FORBIDDEN` to both. On a phone it is the one section beside Огляд and the Kill switch that opens, as a list of cards reached from Ще.

**A Service is a row of its own table.** `services` keeps the id (from the database), a unique name, the kind, the plan, the monthly price in USD cents, the billing day, the plan's limits, the block's place on the canvas and the links to other Services. A link names the other Service and is `constant` or `scheduled`; the API answers it by the other's id. The kind says what the block shows: `railway` its Online / Offline, `cron` its last and next run, `metered` its usage against its limits. The migration seeds the eleven known Services: Railway, Neon, Cloudflare, GitHub, Expo/EAS, Sentry, PostHog, Zoho Mail, Apple Developer / App Store Connect, Google Play and the Telegram bot. Places are fixed data: no dragging.

**The links of the seed.** Railway (the backend) → Neon, Sentry, PostHog and Zoho Mail; Cloudflare → Railway; GitHub → Railway and Cloudflare (Pages); Expo/EAS → Apple Developer / App Store Connect and Google Play (the app); both stores → Railway (the app calls the backend), all constant; Railway → the Telegram bot is scheduled (the alerts Cron).

**A Railway-like canvas.** Each Service is a block absolutely placed at its position over an SVG layer of lines: solid for a constant link, dashed for a scheduled one. The black background with white dots stays dark whatever the admin's theme: the canvas sets `data-theme="dark"` for itself, and the rest of the admin is unchanged. A block opens a side panel, the admin's native modal `<dialog>` (ADR 0160). Under the admin's phone width (`md`) the canvas becomes a list of cards that open the same panel.

**One usage port, an adapter per provider.** `UsagePort` in `server-core` answers a `ServiceReading` by the Service's kind: a metered Service its usage per limit (name, unit, used, limit), a Railway service also Online or Offline, a Cron its last run and its next. Each provider is an adapter of it in the backend, keyed by the Service's name, and reads with a key from the Deployment's environment, never from the Vault. Sentry reuses Якість's `SENTRY_AUTH_TOKEN` and `SENTRY_ORG`: one call to the organization's stats for the errors accepted this calendar month (UTC), against the Developer plan's 5,000. PostHog reuses the Аналітика's `POSTHOG_PERSONAL_API_KEY`: one HogQL count of this month's events, against the free plan's 1,000,000. An unset key or a failed read answers `unavailable`.

**Railway answers the backend and the Crons.** One adapter reads Railway's GraphQL API (`backboard.railway.com/graphql/v2`) with `RAILWAY_READ_TOKEN`, a workspace token kept on the backend and the alerts Cron alone, in the project and environment Railway sets on the Deployment (`RAILWAY_PROJECT_ID`, `RAILWAY_ENVIRONMENT_ID`). One request answers four ports: `Railway` is Online while the latest deployment of the `backend` service is `SUCCESS`, with this calendar month's spend (CPU, memory, egress and volume at Railway's prices) against the Hobby plan's included $5; `alerts`, `quote-check` and `recordings` answer their Cron's last run (its latest deployment `SUCCESS`, or `CRASHED` / `FAILED`, at its update time; none while it has not ended) and `nextCronRunAt`. The ports read together share the one request. A Cron shows on the canvas once the Власник adds a `cron` Service of its Railway name; the seed has none.

**Neon, GitHub Actions and Cloudflare.** Neon reads the project with `NEON_API_KEY` and `NEON_PROJECT_ID` from Neon's management API (`GET /api/v2/projects/{id}`): this period's compute (CU-hours), storage and egress (decimal GB) against the free plan's 100, 0.5 and 5. No read reaches the database, so the bar never wakes the compute or adds to the egress it shows. GitHub Actions reuses Розробка's `GITHUB_TOKEN`, given the account permission Plan: read: one billing usage report of the repository owner's calendar month, its Actions minutes summed against GitHub Free's 2,000. Cloudflare reads with `CLOUDFLARE_API_TOKEN` (Account Analytics: Read) on the Media Store's `R2_ACCOUNT_ID` and `R2_BUCKET`: one GraphQL Analytics query for the bucket's storage and its Class A and B operations this month, against R2's free 10 GB, 1,000,000 and 10,000,000, and the account's Worker requests today against the free 100,000 a day. The site is on GitHub Pages (ADR 0125) and the zone's free plan meters no requests, so neither has a bar. Each adapter is one request a read.

**Usage is cached for an hour.** Every read goes through the cached read of `server-core` (`cachedRead`), in memory, one per Service: within an hour the kept reading comes back and the provider is not asked. `admin.services.usage` answers every ported Service's reading with its read time, apart from `admin.services.list`, so the canvas never waits for a provider. «Оновити» (`admin.services.refreshUsage`, a Власник write) reads one Service's provider at once. A failed read keeps the last good reading, marked stale with its old read time; with none kept the block says «не вдалося прочитати». A restart forgets the cache, so the first page after it reads each provider once.

**The Service entries and the Vault.** A Service entry is a row of `service_entries`: its Service, a type (`login`, `link`, `password`, `token`, `recovery-codes`), a label and a note of where it is used. A login and a link keep their value in the open; a password, token or recovery codes keep it only sealed in the Vault, so a copy of the database alone reveals nothing. The Vault seals with AES-256-GCM under `VAULT_KEY`, a Deployment variable of the backend: 32 random bytes in base64 (`openssl rand -base64 32`), parsed once in the backend config, refused when it is the `AUTH_SECRET`. It is apart from `AUTH_SECRET` and from the TOTP `SecretVault`, so rotating the sign-in secret never touches the entries; each value takes a fresh 12-byte IV. Lost or changed, the key loses every sealed entry by design: the owner keeps a copy outside Railway. Without `VAULT_KEY` the Vault is off: every entry write answers `VAULT_OFF` (503) and the section says so. A Власник adds, changes and deletes entries through `/v1/admin/services.*` with the confirmation and a `ReasonSchema` reason (ADR 0122); an Адмін and an Агент are refused. No read answers a sealed value: the list gives a sealed entry without it and the panel masks it. Each write's Action log row names the Service, the entry, its type and the changed fields, never a value before or after. There is no export.

**The TOTP unlock.** A sealed value opens only after the Власник enters a fresh TOTP code (`/v1/admin/services/vault/unlock`): the code must be of a step newer than the last one spent, so the code that signed in never opens the Vault, and wrong codes count against their own limit (three, then 15 minutes blocked: `WRONG_CODE` with the attempts left, then `TOO_MANY_REQUESTS`). The code opens the calling admin session alone for 15 minutes; the window is kept in the backend's memory by the session, never in the database, so a restart or a sign-out locks the Vault again and no migration holds it. Inside it «Показати» and «Копіювати» (`revealEntry`, `copyEntry`) answer one entry's plain value; outside it they answer `LOCKED` (423). Each answered read writes an Action log row `service.entry.reveal` or `service.entry.copy` naming the Service, the entry and its type, never the value. The admin hides a shown value after 30 s and copies to the clipboard without rendering the value.

**Money by hand.** The Власник enters a Service's plan, monthly price (USD cents) and billing day, and adds a Service by name and kind; each write takes a confirmation and a `ReasonSchema` reason and appends an Action log row: `service.add` with the fields entered, or `service.money.edit` with the Service's name and only the fields that changed, before and after (none when nothing changed). A new Service takes the first place, row by row on a 300 × 140 px grid, whose block keeps 20 px clear of every other block. The list answers the monthly total, the priced Services summed, and the next charge: the nearest Kyiv day, today included, on which a Service with a price above zero and a billing day charges, a billing day past the month's end charging on its last day; the backend counts both by its clock.

**The money in hryvnias at the NBU rate.** The amounts stay in USD cents; the admin shows them in UAH at the NBU's official rate of the dollar, which `services.usdRate` answers with its day. The backend reads the NBU's open API (no key, about 150 bytes) through `NbuPort` at most once a Kyiv day, on the first ask of that day, and keeps the read in Postgres, a failed read included, so a restart reads no second time and a failed day is not retried: it answers the last known rate, marked `last-known`, until the next Kyiv day reads again; `null` while no read ever found one. The reads are rows of the sourcing cache, one a day under the day's NBU page, so the rate needs no table of its own; the in-memory source cache is not used, as a restart would forget it. The admin rounds the hryvnias to whole ones and names the rate and its day. The USD/UAH switch sits by the total and in a Service's panel; the pick is the device's, kept in `localStorage` as the Theme is, dollars when storage holds none or is blocked. A rate in the `list` answer was rejected: a slow or failed NBU read would hold the canvas back.

**A Service at 90 % of a limit.** A limit used to 90 % or more (`NEAR_LIMIT_SHARE` in the contracts) marks the Service's block and panel yellow and raises the Alert kind `service-limit` in the alerts Cron (amends 0088). The Cron reads the same usage ports as «Сервіси», with the backend's keys as Railway references, in the first run of each UTC hour alone: one read of each provider an hour, as the backend keeps it. The alerts table's unique key `service-limit:<Service>:<limit>:<YYYY-MM>` keeps one Alert per Service, limit and period, the calendar month in UTC the ports read, so no migration; a daily limit (the Worker's requests) alerts once a month too. The message goes to the owner's Telegram chat like every Cron Alert and shows in Огляд.

## Considered Options

- **The Services as a section of Безпека**: rejected. Безпека is about people and tokens; the Services need a canvas of their own.
- **Places computed by a layout library**: rejected. Eleven fixed places are simpler and read the same every time.
- **Railway's Crons as Services of their own**: rejected for now. A Service is an outside provider; the Crons are parts of the Deployment on Railway.
- **Usage kept in Postgres**: rejected. An hour of freshness in memory costs one read per provider an hour and a restart; a table would add a migration for numbers that are an hour old anyway.
- **Billing APIs for usage**: rejected. Sentry's and PostHog's billing endpoints need wider scopes than the keys SLOVO already holds; the organization stats and a HogQL count need none.

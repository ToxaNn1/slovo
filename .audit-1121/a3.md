# Audit 2026-11-21, group a3

Scope: `apps/backend/src/{logger,error-reporter,sentry-reporter,error-text}.ts`, `apps/backend/src/development/eas-source.ts`;
`packages/language-pack/src/{pack-reader,cli,report}.ts`; `packages/config/*.js`;
`apps/admin` screens Огляд (`components/overview/overview.tsx`), Аналітика (`routes/analytics.tsx`),
Якість (`routes/quality.tsx`), Розробка (`routes/development.tsx`, `components/development/blocks.tsx`).

Checked against ADR 0048 (crash reports carry no personal data), 0089/0199 (one Feature Switch per condition),
0004 (EAS read-only), 0163 (reader counts), spec #333 (log lines carry no personal data).

Findings a3.1 to a3.3 were reproduced with a throwaway vitest file that fed errors to `createLogger` and read the
JSON lines. It was deleted afterwards. a3.7 was reproduced with ESLint's `Linter` on the rule.

## Findings

### a3.1: CONFIRMED, medium: an AggregateError's inner errors reach the log unscrubbed
- Where: `apps/backend/src/logger.ts:53`
- Defect: `serializeError` spreads `pino.stdSerializers.err(error)` and replaces only `message` and `stack`. For an
  `AggregateError`, pino's serializer also adds `aggregateErrors`: each inner error with its raw `message` and
  `stack`. Neither goes through `scrubbed()` or the DrizzleQueryError/DatabaseError branches.
- Consequence: `log.error({ err: new AggregateError([new Error('anna@mail.com sent 123456')], 'many') })` logs
  `"aggregateErrors":[{"message":"anna@mail.com sent 123456",...}]`. That breaks spec #333. `Promise.any`,
  Node's happy-eyeballs `connect` and some SDKs throw AggregateError. An inner DrizzleQueryError would also log its
  message, which quotes the query's params.
- Fix: drop `aggregateErrors` from the spread and add `errors: error.errors.map((e) => serializeError(e, shown))`
  when `error instanceof AggregateError`. Add a case to `leak.test.ts`.

### a3.2: CONFIRMED, medium: an error's other own properties are logged raw, and redaction stops two levels down
- Where: `apps/backend/src/logger.ts:53` and `:76`
- Defect: the stdSerializer copies every enumerable own property of an Error (e.g. `detail`, `body`, `idToken`,
  `response`, `config`) into the line without scrubbing. The safety net, the redact paths, covers only `email`,
  `code`, `token` and `authorization` at `x`, `*.x` and `*.*.x`. A cause chain nests deeper: `err.cause.cause.email`
  is `*.*.*.email`.
- Consequence: reproduced. `Object.assign(new Error('boom'), { detail: 'anna@mail.com', idToken: 'abc' })` logs
  both values in plain text. An error two causes down that carries `email` is logged unredacted. Library errors
  (auth, mail and HTTP clients) commonly carry the request body or the address as properties.
- Fix: build the serialized error from an allow-list (`type`, `message`, `stack`, `errorCode`, `cause`, plus
  `errors` for a3.1) instead of spreading pino's output. Alternatively, run `scrubbed()` over every string property
  recursively. Either way, the depth no longer matters.

### a3.3: CONFIRMED, low: a thrown non-Error is logged as it is
- Where: `apps/backend/src/logger.ts:52`
- Defect: `if (!(error instanceof Error)) return error;`. A thrown string or plain object goes to the line
  unchanged. Its report (`error-reporter.ts:50`) rightly says only `typeof`.
- Consequence: reproduced. `log.error({ err: 'string anna@mail.com 123456' })` logs the email and the code.
- Fix: return `{ type: 'NonError', message: typeof error === 'string' ? scrubbed(error) : typeof error }`.

### a3.4: PLAUSIBLE, low: `scrubbed()` misses a percent-encoded email
- Where: `apps/backend/src/error-text.ts:5`
- Defect: the email pattern needs a literal `@`. A message that quotes a URL or form body has `anna%40mail.com`,
  which no pattern matches. It is 15 characters, under the token pattern's 20.
- Consequence: a fetch or HTTP-client error that quotes a request URL with an email query parameter goes to the
  logs and to Sentry with the address (ADR 0048).
- Fix: add `/[^\s@"'<>()[\]%]+%40[^\s"'<>()[\]]+/gi` → `[email]`, plus a case in `error-reports.test.ts`.

### a3.5: CONFIRMED, low: Розробка shows nothing when its read fails or is loading
- Where: `apps/admin/src/routes/development.tsx:21-39`
- Defect: GitHub and EAS render only when `development.data` is defined. There is no `isError` branch and no
  pending state. The query also keeps TanStack's default 3 retries, against the policy in `queries.ts` ("A failed
  read shows its notice at once (no retries)"). Огляд's `development` and `alerts` queries do the same
  (`overview.tsx:123-132`).
- Consequence: when `/admin/development` fails (5xx, network, an ended Session), the owner sees only the owner
  checks. Nothing says GitHub/EAS are unavailable; the page looks as though both sources were removed. On Огляд,
  «GitHub недоступний» appears only after about 7 s of retries.
- Fix: render both `Source` blocks as unavailable on `development.isError`, show «Завантаження…» while pending,
  and move the read into a shared `developmentQuery` with `retry: false` in `queries.ts`, used by both screens.

### a3.6: CONFIRMED, low: Аналітика hides failures of the Counters, Edition cards and Variants
- Where: `apps/admin/src/routes/analytics.tsx:102-117`, `:146-158`
- Defect: `counters`, `cards` and `features` have no error branch, and they keep the default retries. If `counters`
  fails, the Community Counters block disappears. If `features` fails, the «Варіанти» heading shows with nothing
  under it, neither results nor «Немає A/B-тестів». If `cards` fails, the Counters show with no answer names
  (`cards.data ?? []`).
- Consequence: the owner reads a missing block as "no data" rather than "source down".
- Fix: add an «… недоступні» notice per query and `retry: false`, like `readers`/`overview` above them.

### a3.7: CONFIRMED, low: `one-switch-per-condition` misses two common shapes (ADR 0089)
- Where: `packages/config/switch-lint.js:1-10`, `:83-89`
- Defect: the rule visits only `LogicalExpression`. `e.isFeatureEnabled('a') ? e.isFeatureEnabled('b') : false`
  passes. So does `const on = e.isFeatureEnabled?.('a'); if (on && e.isFeatureEnabled('b'))`: the `const`
  initializer is a `ChainExpression`, which `isSwitchQuestion` does not unwrap.
- Consequence: a dependency between two switches can be written in the Core without the lint noticing. That is
  what ADR 0089/0199 say belongs in the catalogue's dependencies.
- Fix: also check `ConditionalExpression` (test and consequent/alternate both asking), unwrap `ChainExpression` in
  `isSwitchQuestion`, and add both as `invalid` cases in `switch-lint.test.js`.

### a3.8: CONFIRMED, low: the Sentry reporter has no test
- Where: `apps/backend/src/sentry-reporter.ts:29-39`
- Defect: no test imports `createSentryReporter`. `error-reports.test.ts` checks only the `ErrorReport` that a fake
  reporter receives. Nothing checks what reaches Sentry: the `beforeSend` that strips `request`/`user`/
  `breadcrumbs`, the rebuilt `stack`, or the absence of the default integrations.
- Consequence: an SDK upgrade (`@sentry/node` ^11) that renames `dataCollection` or changes `beforeSend` would
  send request data with no test failing. ADR 0048 is guarded only by reading the code.
- Fix: a test with a fake transport (`transport: () => ({ send, flush })`) that captures one envelope, then asserts
  it holds no `request`, `user` or `breadcrumbs`, and that the exception holds the scrubbed message and frames.

### a3.9: PLAUSIBLE, low: `build:pack` can hang or fail after writing the pack
- Where: `packages/language-pack/src/cli.ts:104-108`
- Defect: Starter Media is downloaded after `buildFrom*` has written `language-pack.db`, with a bare `fetch` and no
  timeout. A refused file throws out of `main()` as an unhandled rejection. A stalled server hangs the command.
- Consequence: an app build step that runs `build:pack` can stall without end. Or it can fail with a stack trace
  while a fresh pack sits in `dist/` next to partial Starter Media, so a re-run or a cached step may ship them out of
  step.
- Fix: `fetch(url, { signal: AbortSignal.timeout(30_000) })`. Catch the download failure in `main()` and return 1
  with one line, like the snapshot failure above it.

### a3.10: PLAUSIBLE, low: one unknown EAS value makes the whole EAS block unavailable
- Where: `apps/backend/src/development/eas-source.ts:28-37`
- Defect: `platform` and `status` are closed `z.enum`s inside `z.array`. One build with a value Expo adds later
  fails the parse of the whole answer.
- Consequence: Розробка shows «EAS недоступний» for every build because of one row. The warning in the log is the
  only clue.
- Fix: parse `status` as `z.string()` and map unknown values to `'in-progress'`. Alternatively, drop the rows that
  fail with `z.array(z.unknown())` plus a per-row `safeParse`.

## Checked, no defect found
- `error-reporter.ts`, `error-text.ts` `framesOf`/`namesOf`/`nameOf`: the Drizzle and Postgres paths leave params,
  message and detail out.
- `pack-reader.ts`: the member stress index (`stressOf(position + 1)`) matches `record-rows.ts:300`. A retired Word
  linked from a Synonym Row reads back as text. `getEntries` order is "no set order" by port contract. Every
  `IN` list is chunked at 500.
- `report.ts`: an empty Category list gives `Math.max()` = `-Infinity`, and `padEnd` treats that as 0, so there is
  no crash.
- `token-lint.js`, `test-reports.js`, `prettier.config.js`, `eslint.config.js`: rules do what their doc comments say.
- Огляд «Зареєстровані читачі … в усіх виданнях» is correct: the count is global by design (ADR 0163,
  `reader-counts.tsx`).
- Якість: CI runs come ascending (`ci-run-store.ts:26`), so `runs.at(-1)` is the latest.
